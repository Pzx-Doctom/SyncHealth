## 1. Pydantic 数据校验进阶

### 1.1 Field() 完整参数

`Field()` 是 Pydantic 中最常用的字段校验工具，它为模型字段添加约束条件和文档元信息。与直接使用类型注解（如 `name: str`）相比，`Field()` 可以精确控制字段的取值范围、长度、格式等规则，使数据校验在模型定义阶段一次性完成，无需在业务代码中手动判断。

`Field()` 的参数按用途可分为三类：

- **约束参数**：根据字段类型不同而不同。字符串支持 `min_length`/`max_length`/`pattern`（正则）；数值支持 `gt`（大于）/`ge`（大于等于）/`lt`（小于）/`le`（小于等于）/`multiple_of`（倍数）；列表支持 `min_length`/`max_length` 控制元素数量。
- **默认值参数**：`default=...` 表示必填（`...` 即 `Ellipsis`），`default=None` 表示可选且默认为 None，也可指定具体默认值如 `default=[]`。
- **文档参数**：`title`、`description`、`examples` 用于生成 OpenAPI 文档，让接口文档更易读。

下面通过一个商品模型，演示字符串、数值、列表、可选字段四类场景下 `Field()` 的完整用法：

```python
from pydantic import BaseModel, Field
from typing import Optional

class Product(BaseModel):
    # 字符串类型的完整约束
    name: str = Field(
        default=...,                    # ... 表示必填（省略 default 也是必填）
        min_length=1,                   # 最小长度
        max_length=200,                 # 最大长度
        pattern=r"^[\u4e00-\u9fa5a-zA-Z0-9\s]+$",  # 正则校验
        title="商品名称",               # 文档标题
        description="商品的中文或英文名称",  # 文档描述
        examples=["iPhone 15"]          # 文档示例
    )

    # 数值类型的完整约束
    price: float = Field(
        gt=0,                           # greater than（大于）
        ge=0.01,                        # greater than or equal（大于等于）
        lt=999999,                      # less than（小于）
        le=999999,                      # less than or equal（小于等于）
        multiple_of=0.01,               # 必须是 0.01 的倍数
        description="商品价格（元）"
    )

    # 列表类型约束
    tags: list[str] = Field(
        default=[],
        min_length=0,                   # 最少元素数
        max_length=10,                  # 最多元素数
        description="商品标签"
    )

    # 可选字段可以指定默认值
    discount: Optional[float] = Field(
        default=None,
        ge=0,
        le=1,                           # 折扣范围 0~1
        description="折扣率，0.8 表示八折"
    )
```

### 1.2 @validator 自定义校验器

`Field()` 虽然强大，但只能进行单字段的静态约束（如长度、范围、正则）。它的局限性在于：所有校验规则必须在定义字段时写死，无法根据其他字段的值或运行时的数据来动态决定校验逻辑。

所谓**动态判断**，是指校验结果依赖运行时条件，而非固定的参数值。例如：

- `Field(ge=0, le=100)` 只能规定年龄在 0~100，但如果你需要"如果是学生则年龄 ≤ 25，如果是成人则年龄 ≥ 18"，这种根据用户身份变化的条件逻辑，`Field()` 做不到，必须用 `@validator` 写 `if/else` 分支。
- 再比如"用户名不能是已注册的"，这需要查询数据库，属于运行时判断，`Field()` 无法胜任。

所谓**字段间关系**，是指一个字段的合法性取决于另一个字段的值。例如：

- "确认密码"必须和"密码"字段一致——这两个字段的校验彼此关联。
- "结束日期"必须晚于"开始日期"——需要同时访问两个字段才能判断。
- "年龄"应该和"生日"匹配——需要将两个字段的值做逻辑运算。

这些场景下，`Field()` 无能为力，必须使用 `@validator` 获取已校验的其他字段值（通过 `values` 参数）来进行跨字段判断。

`@validator` 和 `@root_validator` 的区别：

- `@validator("字段名")` 括号里写的是**模型中的某个字段名**（如 `"username"`、`"age"`、`"confirm_password"`），表示这个校验函数只针对该字段执行。你也可以传入多个字段名，如 `@validator("password", "confirm_password")` 同时对两个字段生效。

- `@root_validator` 则不同：它**没有字段名参数**，而是作用于模型的整体。它与 `@validator` 在参数上最大的区别是：
    - `@validator("字段名")` → 第一个参数是字段名字符串
    - `@root_validator(skip_on_failure=True)` → 只有可选的关键字参数，没有字段名

`skip_on_failure` 的含义：

Pydantic 的校验是按字段声明顺序依次执行的。假设当前模型顺序为 `username → password → confirm_password → age → birthday`，如果 `username` 在 `@validator` 中就已经校验失败了（比如包含非法字符），那么后面的字段校验会被跳过，`values` 中只有部分字段值。

`@root_validator` 默认行为：无论前置字段是否校验成功，都会执行。此时如果 `values` 中缺少 `age` 或 `birthday`（因为前置校验失败导致这些字段根本没进入校验流程），就可能出现 `KeyError` 或误判。

`skip_on_failure=True` 的作用：**如果前置字段的校验已经失败了，就自动跳过这个 `root_validator`，不再多此一举**。这是推荐的安全写法，避免因数据不完整导致 `root_validator` 内部崩溃。

下面以用户注册模型为例，演示字段级校验（用户名格式、年龄范围、密码确认）和跨字段校验（年龄与生日匹配）：

```python
from pydantic import BaseModel, validator, root_validator
from datetime import date

class UserRegister(BaseModel):
    username: str = Field(min_length=3, max_length=20)
    password: str = Field(min_length=6, max_length=32)
    confirm_password: str
    age: int
    birthday: date

    # 字段级别的校验器
    @validator("username")
    def username_must_be_alphanumeric(cls, v: str) -> str:
        """用户名只能包含字母数字"""
        if not v.isalnum():
            raise ValueError("用户名只能包含字母和数字")
        return v.strip()  # 自动去除前后空格

    @validator("age")
    def age_must_be_reasonable(cls, v: int) -> int:
        """年龄必须合理"""
        if v < 0:
            raise ValueError("年龄不能为负数")
        if v > 150:
            raise ValueError("年龄不能超过 150 岁")
        return v

    @validator("confirm_password")
    def passwords_match(cls, v: str, values) -> str:
        """确认密码必须与密码一致"""
        # values 是已经校验过的字段字典
        if "password" in values and v != values["password"]:
            raise ValueError("两次输入的密码不一致")
        return v

    # 跨字段校验（Pydantic V1 风格）
    @root_validator(skip_on_failure=True)
    def check_age_vs_birthday(cls, values):
        """验证年龄和生日的合理性"""
        age = values.get("age")
        birthday = values.get("birthday")
        if age is not None and birthday is not None:
            today = date.today()
            expected_age = today.year - birthday.year
            if abs(expected_age - age) > 1:
                raise ValueError(
                    f"年龄({age})与生日({birthday})不匹配，预期年龄约{expected_age}岁"
                )
        return values
```

### 1.3 常用 Pydantic 特殊类型

除了 `str`、`int`、`float` 等基础类型外，Pydantic 还内置了一系列特殊类型，它们封装了常见格式校验逻辑，可以直接在字段定义中使用，免去手写正则表达式的麻烦。

这些特殊类型可分为几类：

- **格式校验类型**：`EmailStr`（邮箱格式）、`HttpUrl`/`AnyUrl`（URL 格式）、`IPvAnyAddress`（IPv4/IPv6 地址），传入非法格式时会自动报错。
- **敏感数据类型**：`SecretStr`/`SecretBytes` 在日志和调试输出中显示为 `**********`，避免密码、密钥等敏感信息泄露。
- **路径类型**：`FilePath`（必须指向已存在的文件）、`DirectoryPath`（必须指向已存在的目录），适合配置类场景。
- **日期约束类型**：`PastDate`（必须是过去的日期）、`FutureDate`（必须是未来的日期），适合生日、预约时间等场景。
- **约束类型**：`conint`、`confloat`、`constr`、`conlist` 是 `Field()` 的简写形式，可以直接在类型注解中写入约束条件，适合简单场景下快速定义模型，如 `conint(ge=0, le=100)` 等价于 `int = Field(ge=0, le=100)`。

下面演示在一个用户档案模型中综合使用这些类型：

```python
from pydantic import (
    BaseModel,
    EmailStr,           # 邮箱格式
    HttpUrl,            # HTTP URL
    AnyUrl,             # 任意 URL
    IPvAnyAddress,      # IP 地址
    SecretStr,          # 敏感字符串（日志中隐藏）
    SecretBytes,        # 敏感字节
    FilePath,           # 文件路径
    DirectoryPath,      # 目录路径
    PastDate,           # 过去的日期
    FutureDate,         # 未来的日期
    conint,             # 受限整数
    confloat,           # 受限浮点数
    constr,             # 受限字符串
    conlist,            # 受限列表
)
from typing import Optional

class UserProfile(BaseModel):
    email: EmailStr                 # 自动验证邮箱格式
    website: Optional[HttpUrl] = None  # 自动验证 URL 格式
    ip_address: Optional[IPvAnyAddress] = None
    birth_date: PastDate            # 必须是过去的日期

    # 直接使用约束类型（不需要 Field）
    score: conint(ge=0, le=100)           # 受限整数：0~100
    rating: confloat(ge=0.0, le=5.0)      # 受限浮点数：0~5
    nickname: constr(min_length=2, max_length=20)  # 受限字符串
    hobbies: conlist(str, min_length=1, max_length=5)  # 受限列表
```

> **注意**：使用 `EmailStr` 需要安装 `pip install pydantic[email]`

### 1.4 模型中的 Config 类

`Config` 是 Pydantic 模型内部的配置类，用于定义模型的全局行为选项。当模型的默认行为无法满足需求时，可以通过 `Config` 进行定制。

常用的 `Config` 选项包括：

- **`from_attributes = True`**（旧版叫 `orm_mode = True`）：允许从 ORM 对象（如 SQLAlchemy 模型实例）创建 Pydantic 模型，FastAPI 会自动从对象的属性中提取值，这是连接数据库层与 API 层的关键配置。
- **`str_strip_whitespace = True`**：自动去除字符串字段的前后空格，避免用户输入多余空格导致校验或匹配失败。
- **`validate_assignment = True`**：在实例创建后修改属性时也触发校验（默认只在创建时校验），保证数据在整个生命周期内始终合法。
- **`json_schema_extra`**：为 OpenAPI 文档添加示例数据，使 Swagger UI 中显示请求示例，提升接口文档的可读性。

下面演示一个完整的 `Config` 配置示例：

```python
class User(BaseModel):
    id: int
    name: str
    _secret: str = ""  # 以下划线开头的私有属性

    class Config:
        # ORM 模式：允许从 ORM 对象创建模型
        from_attributes = True

        # 字符串去除前后空格
        str_strip_whitespace = True

        # 允许使用可变默认值（禁用以防止共享引用问题）
        validate_assignment = True

        # 示例数据
        json_schema_extra = {
            "example": {
                "id": 1,
                "name": "张三"
            }
        }

        # 字段的别名映射
        # 如果用 from_attributes=True 从数据库对象创建，字段名可以不同
        # 例如数据库字段是 user_name，模型是 username
```

## 2. 响应模型与状态码

### 2.0 为什么需要响应模型？

在实际开发中，接口返回的数据往往包含一些不应暴露给前端的敏感字段（如密码哈希、内部状态码、创建者 ID 等）。如果不加控制地将数据库中的数据直接返回，就可能导致信息泄露。

**没有响应模型**时，路由函数返回什么客户端就收到什么，开发者必须手动删除敏感字段，既容易遗漏又难以维护：

```python
@app.post("/users/")
def create_user(user: UserCreate):
    # 返回了密码哈希！
    return {"id": 1, "username": user.username, "password_hash": "abc123..."}
```

**有响应模型**时，只需在装饰器上声明 `response_model`，FastAPI 会自动按模型定义过滤返回数据，敏感字段被拦截，无需手动处理：

```python
@app.post("/users/", response_model=UserResponse)
def create_user(user: UserCreate):
    # 只返回 UserResponse 中定义的字段，自动过滤掉密码
    user_dict = user.dict()
    return user_dict
```

> **注意**：上面 2.0 是概念示意——`UserResponse` 只是提前亮个相。在真正的代码文件里，`UserResponse` **必须先定义、后使用**，否则 Python 会报 `NameError`：
>
> ```python
> # ❌ Python 逐行执行，读到这行时 UserResponse 还不存在 → 报错
> @app.post("/users/", response_model=UserResponse)   # NameError!
>
> # ✅ 类定义必须写在装饰器之前
> class UserCreate(BaseModel):       # 1. 先定义
>     username: str
>     password: str
>
> class UserResponse(BaseModel):     # 2. 先定义
>     id: int
>     username: str
>
> @app.post("/users/", response_model=UserResponse)   # 3. 再用
> def create_user(user: UserCreate):
>     ...
> ```
>
> 实际项目中 Schema 定义在独立文件里，通过 `import` 引入——`import` 写在文件顶部，引用时类一定已存在，自然就不会有顺序问题：
>
> ```python
> # backend/app/api/auth.py
> from app.schemas.auth import UserRegister, TokenResponse   # import 时已定义
>
> @router.post("/register", response_model=TokenResponse)    # 直接用，安全
> async def register(data: UserRegister, db = Depends(get_db)):
>     ...
> ```

### 2.1 response_model 基本用法

`response_model` 是 FastAPI 中控制接口返回数据的核心机制。通过在路由装饰器上声明 `response_model`，FastAPI 会自动过滤返回结果，只输出模型中定义的字段，从而避免敏感信息（如密码）泄露。

使用 `response_model` 的关键点：

- **入参模型与出参模型分离**：创建用户时需要接收密码（`UserCreate`），但返回时不应包含密码（`UserResponse`），这种"读写分离"是 API 设计的最佳实践。
- **自动过滤机制**：即使路由函数返回的字典中包含 `password` 字段，只要 `UserResponse` 中没有定义该字段，FastAPI 就会自动将其过滤掉。
- **自动类型转换**：返回数据会按照 `response_model` 的字段类型进行转换，如字符串日期转为 `datetime` 对象。
- **文档生成**：`response_model` 会自动反映到 Swagger UI 中，前端开发者可以直接看到接口的返回结构。

> ### 🏗️ 项目实例：SyncHealth 注册接口的 response_model
>
> SyncHealth 注册接口中，用户提交 `UserRegister`（含 `password`），但通过 `response_model=TokenResponse` 确保响应只返回 JWT token，密码不会泄露：
>
> ```python
> # backend/app/api/auth.py - 注册端点：response_model 过滤敏感字段
> @router.post("/register", response_model=TokenResponse)
> async def register(data: UserRegister, db: AsyncSession = Depends(get_db)):
>     user, access_token, refresh_token = await register_user(
>         db, data.email, data.password, data.display_name
>     )
>     # 虽然 service 层返回了 user 对象（含 hashed_password），
>     # 但 response_model=TokenResponse 只输出 access_token 和 refresh_token
>     return TokenResponse(access_token=access_token, refresh_token=refresh_token)
> ```
>
> 获取当前用户信息的 `/auth/me` 端点则使用 `response_model=UserResponse`，确保 `hashed_password` 永远不会出现在响应中：
>
> ```python
> @router.get("/me", response_model=UserResponse)
> async def me(current_user: User = Depends(get_current_user)):
>     return UserResponse(
>         id=current_user.id,
>         email=current_user.email,
>         display_name=current_user.display_name,
>         created_at=current_user.created_at.isoformat(),
>     )
> ```

下面定义一个创建用户的接口：入参模型 `UserCreate` 包含密码，而出参模型 `UserResponse` 不含密码，即使内部数据带有密码字段，最终响应也会被自动过滤：

```python
from pydantic import BaseModel
from typing import Optional

# 创建模型（包含密码）
class UserCreate(BaseModel):
    username: str
    password: str
    email: str

# 响应模型（不含密码）
class UserResponse(BaseModel):
    id: int
    username: str
    email: str
    is_active: bool = True

# 模拟数据库
fake_db = {}
user_counter = 0

@app.post("/users/", response_model=UserResponse)
def create_user(user: UserCreate):
    global user_counter
    user_counter += 1
    # 存入数据库
    fake_db[user_counter] = {
        "id": user_counter,
        "username": user.username,
        "password": user.password,  # 实际应用中会被哈希
        "email": user.email,
        "is_active": True
    }
    # 返回字典，FastAPI 自动用 UserResponse 过滤掉 password
    return fake_db[user_counter]
```

**过滤发生在哪里？** 不是在 `return` 语句里。完整的执行流程是这样的：

```
① 路由函数执行完毕
   return fake_db[user_counter]
   → 返回 {"id": 1, "username": "张三", "password": "secret", "email": "z@test.com", "is_active": true}

② FastAPI 拦截返回值，用 response_model=UserResponse 进行校验和转换
   UserResponse 定义的字段：id、username、email、is_active
   password 不在 UserResponse 的定义中 → 被丢弃

③ 最终发给客户端的 JSON：
   {"id": 1, "username": "张三", "email": "z@test.com", "is_active": true}
   password 字段消失了！
```

所以可以这样理解：

- **`return` 决定"要发什么数据"**：路由函数返回什么，FastAPI 就拿什么数据进入下一步。
- **`response_model` 决定"发之前怎么修剪"**：如果声明了 `response_model`，FastAPI 会用模型裁剪一遍再发出；如果没声明，`return` 的数据原样 JSON 序列化后直接发出。

也就是说，`return` 的值**不总是**等于客户端最终看到的内容——取决于装饰器上有没有 `response_model`。开发者不需要在 `return` 之前手动 `del data["password"]`。

### 2.2 过滤返回字段

除了通过 `response_model` 自动过滤外，FastAPI 还提供了 `response_model_include` 和 `response_model_exclude` 参数，用于在路由级别动态控制返回的字段集合。

这两个参数的使用场景：

- **`response_model_include`**：指定只返回哪些字段（白名单模式），适合公开接口，如只返回 `id` 和 `username`。
- **`response_model_exclude`**：指定排除哪些字段（黑名单模式），适合需要大部分字段但隐藏少数敏感字段的场景，如排除 `password` 和 `email`。
- **多接口复用同一数据源**：同一份用户数据，公开页面只返回基本信息，管理后台返回完整信息，无需为每种场景定义单独的响应模型。

下面演示查询用户、公开信息、基本信息三种接口的字段控制方式：

```python
# 方式1：默认返回 UserResponse 的全部字段
@app.get("/users/{user_id}", response_model=UserResponse)
def get_user(user_id: int):
    user = fake_db.get(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
# 返回示例：{"id": 1, "username": "张三", "email": "zhang@example.com", "is_active": true}


# 方式2：response_model_exclude — 排除敏感字段（黑名单模式）
# exclude 写在装饰器参数中，FastAPI 自动从响应里移除 email 字段
@app.get("/users/{user_id}/public", response_model=UserResponse,
         response_model_exclude={"email"})
def get_public_user(user_id: int):
    user = fake_db.get(user_id)
    if user:
        return user
    raise HTTPException(status_code=404)
# 返回示例：{"id": 1, "username": "张三", "is_active": true}
# email 已被自动过滤，不会出现在响应中


# 方式3：response_model_include — 只包含指定字段（白名单模式）
# include 写在装饰器参数中，只有列出的字段会出现在响应中
@app.get("/users/{user_id}/basic", response_model=UserResponse,
         response_model_include={"id", "username"})
def get_basic_user(user_id: int):
    user = fake_db.get(user_id)
    return user
# 返回示例：{"id": 1, "username": "张三"}
# 即使数据库中有 email、is_active，也只输出 id 和 username
```

### 2.3 多响应模型

有些接口需要根据请求参数返回不同结构的响应，例如列表页返回精简信息，详情页返回完整信息。FastAPI 支持通过 `Union[模型A, 模型B]` 声明多个可能的响应模型，FastAPI 会按声明顺序依次尝试匹配返回的数据。

使用 `Union` 多响应模型的要点：

- **按需返回**：通过查询参数控制返回精简版还是详细版，减少不必要的数据传输。
- **匹配规则**：FastAPI 会尝试用 `Union` 中的模型依次校验返回数据，第一个匹配成功的模型即为最终响应结构。
- **文档表现**：Swagger UI 会展示所有可能的响应模型，前端可据此适配不同场景。

下面用一个例子说明：接口根据 `detail` 查询参数，返回 `UserLite`（精简）或 `UserDetail`（详细）两种模型。

**`detail` 如何关联到模型选择？** 注意：`detail` 本身并不直接指定用哪个模型，它和模型之间是通过"返回数据的字段数量"间接关联的：

```
detail=true  → 路由函数 return 完整数据（字段多）→ FastAPI 拿数据去 Union 中逐一匹配
                                                      ↓
                                                  UserDetail 先试：需要的字段数据都有 → 匹配 ✅
                                                      ↓
                                                  UserLite 不再尝试（已找到匹配）

detail=false → 路由函数 return 精简数据（只有 id、username）
                                                      ↓
                                                  UserDetail 先试：缺少 email/is_active/created_at → 失败 ❌
                                                      ↓
                                                  UserLite 再试：只需要 id、username，数据中都有 → 匹配 ✅
```

也就是说，FastAPI 并不关心 `detail` 的值是多少，它只关心路由函数最终 `return` 出来的数据长什么样。数据中有什么字段，就决定了它匹配 Union 中的哪个模型。

**关键点——Union 的顺序决定了匹配优先级**：FastAPI 按 `Union` 中的顺序依次尝试。`UserDetail` 需要更多字段，所以要放在前面先试；`UserLite` 放在后面当"宽匹配"的兜底。

下面看具体代码实现：

```python
from typing import Union

class UserLite(BaseModel):
    """精简用户信息（列表页使用）"""
    id: int
    username: str

class UserDetail(BaseModel):
    """详细用户信息（详情页使用）"""
    id: int
    username: str
    email: str
    is_active: bool
    created_at: str

@app.get("/users/{user_id}", response_model=Union[UserDetail, UserLite])
def get_user(user_id: int, detail: bool = False):
    # fake_db 中存储的数据结构（在 2.1 节中创建）：
    # { 1: {"id": 1, "username": "张三", "password": "xxx", "email": "z@example.com", "is_active": true} }
    # 注意：其中包含 password 字段，但 UserDetail 和 UserLite 都没有定义它，所以永远不会返回密码
    user = fake_db.get(user_id)
    if not user:
        raise HTTPException(status_code=404)

    if detail:
        # 返回完整数据，包含 email、is_active、created_at
        # → UserDetail（第一个）校验：所有必填字段都有值 → 匹配成功 ✅
        return user

    # 只返回 id 和 username，没有 email、is_active、created_at
    # → UserDetail（第一个）校验：缺少字段 → 匹配失败 ❌
    # → UserLite（第二个）校验：只需 id 和 username → 匹配成功 ✅
    return {"id": user["id"], "username": user["username"]}
```

**访问示例**：
- `GET /users/1?detail=false` → 返回 `{"id": 1, "username": "张三"}`，匹配 `UserLite`
- `GET /users/1?detail=true`  → 返回 `{"id": 1, "username": "张三", "email": "z@example.com", "is_active": true, "created_at": "2026-01-01"}`，匹配 `UserDetail`

### 2.4 HTTP 状态码

HTTP 状态码是 RESTful API 语义的重要组成部分，它用三位数字告诉调用方请求的处理结果：2xx 表示成功、3xx 表示重定向、4xx 表示客户端错误、5xx 表示服务器错误。正确的状态码能让调用方准确判断请求结果，无需解析响应体即可知道成功或失败。

FastAPI 设置状态码的两种方式：

- **装饰器参数**：`status_code=status.HTTP_201_CREATED`，适用于状态码固定的场景，如创建资源固定返回 201。FastAPI 的 `status` 模块提供了语义化的常量，比直接写数字更易读。
- **Response 对象**：返回 `JSONResponse(status_code=...)`，适用于状态码需要动态判断的场景，如删除成功返回 204、条件不满足返回其他码。

下面演示创建资源返回 201、删除资源返回 204 的常见用法，并附上常用状态码速查表：

```python
from fastapi import FastAPI, status
from fastapi.responses import JSONResponse

# 方式1：使用装饰器参数
@app.post("/items/", status_code=status.HTTP_201_CREATED)
def create_item(item: Item):
    """创建资源，返回 201 Created"""
    return item

# 方式2：使用 Response 对象
@app.delete("/items/{item_id}")
def delete_item(item_id: int):
    """删除资源，返回 204 No Content"""
    # 没有返回内容时使用 204
    return JSONResponse(status_code=status.HTTP_204_NO_CONTENT)

# 常用状态码
# 200 OK            - 成功（GET/PUT/PATCH）
# 201 Created       - 创建成功（POST）
# 204 No Content    - 成功但无返回内容（DELETE）
# 301 Moved         - 永久重定向
# 302 Found         - 临时重定向
# 400 Bad Request   - 请求参数有误
# 401 Unauthorized  - 未认证
# 403 Forbidden     - 无权限
# 404 Not Found     - 资源不存在
# 422 Unprocessable - 校验失败（FastAPI 自动返回）
# 500 Internal Error- 服务器内部错误
```

### 2.5 响应头与 Cookie

在 Web 开发中，经常需要设置响应头和 Cookie。响应头可用于传递自定义标识（如 `X-Request-ID`）、缓存策略（如 `Cache-Control`）、跨域配置（如 `Access-Control-Allow-Origin`）；Cookie 则常用于维持登录状态、记录用户偏好、追踪访问行为等。

FastAPI 通过注入 `Response` 对象实现响应头和 Cookie 的操作：

- **设置 Cookie**：`response.set_cookie()` 方法接收 `key`、`value`，以及安全相关参数：`max_age`（过期秒数）、`httponly`（设为 True 可防止 JavaScript 读取，防御 XSS）、`samesite`（设为 lax/strict 可防御 CSRF）、`secure`（仅 HTTPS 传输）。
- **设置响应头**：通过 `response.headers["键"] = "值"` 直接添加，适合自定义业务头或调试信息。

下面演示设置带过期时间和安全属性的 Cookie，以及添加自定义响应头：

```python
from fastapi import Response
from datetime import datetime

@app.post("/set-cookie/")
def set_cookie(response: Response):
    """设置 Cookie"""
    response.set_cookie(
        key="last_visit",
        value=datetime.now().isoformat(),
        max_age=3600,           # 1 小时后过期
        httponly=True,          # 只能通过 HTTP 访问
        samesite="lax"          # SameSite 策略
    )
    return {"message": "Cookie 已设置"}

@app.get("/custom-header/")
def custom_header(response: Response):
    """设置自定义响应头"""
    response.headers["X-Custom-Header"] = "my-value"
    response.headers["X-Request-Time"] = str(datetime.now())
    return {"message": "已添加自定义响应头"}
```

### 3.1 表单数据 Form()

不同于 JSON 请求体（使用 Pydantic 模型接收），传统的 HTML 表单提交使用 `application/x-www-form-urlencoded` 格式，数据以 `key=value&key=value` 的形式放在请求体中。此外，登录接口通常需要兼容浏览器原生 `<form>` 表单提交或 OAuth2 密码模式（标准要求表单格式），这时就需要用 `Form()` 而非 JSON 模型。

`Form()` 的使用要点：

- **声明方式**：`username: str = Form(...)`，`...` 表示必填，也可以指定默认值。
- **与 Pydantic 模型的区别**：`Form()` 用于表单字段，Pydantic 模型用于 JSON 体，两者不能在同一个接口中混用（但 `Form()` 可以和 `File()` 混用）。
- **自动文档**：Swagger UI 中会显示为 `x-www-form-urlencoded` 格式的输入框，方便测试。

下面以登录接口为例，演示如何接收用户名和密码两个表单字段：

```python
from fastapi import FastAPI, Form

@app.post("/login/")
def login(username: str = Form(...), password: str = Form(...)):
    """
    接收 application/x-www-form-urlencoded 格式的表单数据
    访问方式：HTML <form> 或 Postman 的 x-www-form-urlencoded
    
    ... = Ellipsis，表示必填
    """
    # ⚠️ 实际项目中密码应该哈希存储，这里仅为示例
    if username == "admin" and password == "secret":
        return {"message": "登录成功", "username": username}
    raise HTTPException(status_code=401, detail="用户名或密码错误")
```

**测试 HTML 表单**：
```html
<form action="http://127.0.0.1:8000/login/" method="post">
    <input type="text" name="username">
    <input type="password" name="password">
    <button type="submit">登录</button>
</form>
```

### 3.2 文件上传 UploadFile

FastAPI 提供了两种文件上传方式：`bytes`（一次性读取到内存）和 `UploadFile`（流式读取）。`UploadFile` 是推荐方式，它采用 `SpooledTemporaryFile` 在内存中暂存小文件、超过阈值自动写入磁盘，因此能处理大文件而不会撑爆内存。

`UploadFile` 的核心属性和方法：

- **`file.filename`**：客户端上传的原始文件名（注意：不可信，需校验后使用）。
- **`file.content_type`**：文件的 MIME 类型，如 `image/png`、`application/pdf`。
- **`file.size`**：文件大小（字节数）。
- **`file.file`**：底层的类文件对象，可用 `shutil.copyfileobj` 逐块复制到目标文件。
- **`await file.read()`**：异步读取全部内容为 `bytes`；`await file.seek(0)` 可重置读取位置。
- **`await file.close()`**：关闭文件，释放资源。

文件上传的常见场景包括单文件上传、多文件批量上传（参数声明为 `list[UploadFile]`）、文件与表单字段混合上传（如上传图片时附带描述和标签，此时文件用 `File()`、其他字段用 `Form()`）。

下面演示这三种场景的完整实现：

```python
from fastapi import FastAPI, File, UploadFile
import shutil
from pathlib import Path

# 创建上传目录
UPLOAD_DIR = Path("uploads")
UPLOAD_DIR.mkdir(exist_ok=True)

@app.post("/upload/single/")
async def upload_single_file(file: UploadFile = File(...)):
    """
    单文件上传
    
    UploadFile 的属性：
    - file.filename    : 原始文件名
    - file.content_type: 文件类型（如 image/png）
    - file.size        : 文件大小
    - file.file        : 类文件对象，用于读取内容
    """
    # 保存文件到本地
    file_path = UPLOAD_DIR / file.filename
    with open(file_path, "wb") as buffer:
        # shutil.copyfileobj 逐块复制，处理大文件
        shutil.copyfileobj(file.file, buffer)

    return {
        "filename": file.filename,
        "content_type": file.content_type,
        "saved_to": str(file_path)
    }

@app.post("/upload/multiple/")
async def upload_multiple_files(files: list[UploadFile] = File(...)):
    """多文件上传"""
    results = []
    for file in files:
        file_path = UPLOAD_DIR / file.filename
        with open(file_path, "wb") as buffer:
            shutil.copyfileobj(file.file, buffer)
        results.append({
            "filename": file.filename,
            "content_type": file.content_type,
            "saved_to": str(file_path)
        })
    return {"uploaded_files": results}

@app.post("/upload-with-metadata/")
async def upload_with_metadata(
    file: UploadFile = File(..., description="要上传的图片"),
    description: str = Form(..., description="图片描述"),
    tags: str = Form("", description="标签，逗号分隔")
):
    """
    文件 + 表单数据混合上传
    注意：文件用 File()，其他数据用 Form()
    """
    file_path = UPLOAD_DIR / file.filename
    with open(file_path, "wb") as buffer:
        shutil.copyfileobj(file.file, buffer)

    return {
        "file": file.filename,
        "description": description,
        "tags": tags.split(",") if tags else [],
        "saved_to": str(file_path)
    }
```

### 3.3 文件上传校验

> ### 🏗️ 项目实例：SyncHealth Apple Health 文件上传
>
> SyncHealth 接收用户上传的 Apple Health 导出文件（`.zip` 或 `.xml`），校验文件扩展名后保存，并通过 `BackgroundTasks` 后台异步解析入库：
>
> ```python
> # backend/app/api/apple_health.py - 文件上传 + 后台任务
> from fastapi import APIRouter, BackgroundTasks, File, UploadFile
>
> router = APIRouter(prefix="/apple-health", tags=["apple-health"])
> ALLOWED_EXTENSIONS = (".xml", ".zip")
>
> @router.post("/upload")
> async def upload_apple_health(
>     background_tasks: BackgroundTasks,
>     file: UploadFile = File(...),
>     current_user: User = Depends(get_current_user),
> ):
>     # 1. 校验文件扩展名
>     filename = (file.filename or "").lower()
>     if not filename.endswith(ALLOWED_EXTENSIONS):
>         raise HTTPException(
>             status_code=400,
>             detail="仅支持 .xml 或 .zip 格式的 Apple Health 导出文件",
>         )
>
>     # 2. 保存文件到磁盘（用 UUID 防冲突）
>     task_id = uuid.uuid4().hex
>     save_name = f"{task_id}_{file.filename}"
>     save_path = os.path.join(upload_dir, save_name)
>     with open(save_path, "wb") as f:
>         shutil.copyfileobj(file.file, f)
>     await file.close()
>
>     # 3. 添加到后台任务，立即返回 task_id
>     background_tasks.add_task(_run_import_task, task_id, save_path, current_user.id)
>     return {"task_id": task_id, "status": "pending"}
> ```
>
> 这个端点展示了三个实战技能的组合：`UploadFile` 接收文件 → 扩展名校验 → `BackgroundTasks` 异步处理。

直接接收用户上传的文件存在严重的安全风险，必须进行严格校验。常见的安全隐患包括：

- **恶意文件伪装**：攻击者将 `.php` 或 `.exe` 文件改名为 `.jpg` 上传，企图执行恶意代码。因此既要校验 MIME 类型（`content_type`），也要校验扩展名，双重验证。
- **超大文件攻击**：攻击者上传超大文件耗尽服务器磁盘和内存。必须限制文件大小，并在读取前或读取后立即检查。
- **路径遍历攻击**：恶意文件名可能包含 `../` 等路径穿越字符，直接拼接保存路径会导致覆盖系统文件。应使用 `os.path.basename` 或 UUID 生成安全文件名。

下面以头像上传为例，演示完整的校验流程：先检查 MIME 类型白名单，再核对扩展名，最后读取内容校验大小，全部通过后才保存文件：

```python
import os
from fastapi import File, UploadFile

ALLOWED_TYPES = {"image/jpeg", "image/png", "image/gif", "image/webp"}
MAX_SIZE = 2 * 1024 * 1024  # 2MB

@app.post("/upload/avatar/")
async def upload_avatar(file: UploadFile = File(...)):
    """上传头像（带校验）"""

    # 1. 校验文件类型
    if file.content_type not in ALLOWED_TYPES:
        raise HTTPException(
            status_code=400,
            detail=f"不支持的文件类型：{file.content_type}，仅支持 {ALLOWED_TYPES}"
        )

    # 2. 校验文件扩展名
    ext = os.path.splitext(file.filename)[1].lower()
    if ext not in {".jpg", ".jpeg", ".png", ".gif", ".webp"}:
        raise HTTPException(status_code=400, detail="不支持的文件扩展名")

    # 3. 校验文件大小（读完全部内容后检查）
    contents = await file.read()
    if len(contents) > MAX_SIZE:
        raise HTTPException(
            status_code=400,
            detail=f"文件过大：{len(contents)} 字节，最大 {MAX_SIZE} 字节"
        )

    # 保存文件
    file_path = UPLOAD_DIR / f"avatar_{file.filename}"
    with open(file_path, "wb") as f:
        f.write(contents)

    return {
        "filename": file.filename,
        "size": len(contents),
        "saved_to": str(file_path)
    }
```

## 4. 错误处理与自定义异常

### 4.1 HTTPException 基本用法

`HTTPException` 是 FastAPI 抛出 HTTP 错误的标准方式。当请求无法正常处理时（如参数非法、资源不存在、权限不足），在路由中通过 `raise HTTPException(...)` 抛出异常，FastAPI 会拦截该异常并自动将其转换为对应的 HTTP 错误响应，无需手动构造 `JSONResponse`。

`HTTPException` 的三个核心参数：

- **`status_code`**：HTTP 状态码，推荐使用 `status` 模块的语义化常量（如 `status.HTTP_404_NOT_FOUND`，本质上：
`status.HTTP_404_NOT_FOUND` 底层就是被赋值为数字 404，等价替换，只是包装成了带含义的常量。），比直接写数字更清晰。
- **`detail`**：错误详情，可以是字符串（简单消息）或字典/列表（结构化错误信息），会作为 JSON 响应体的 `detail` 字段返回给客户端。
- **`headers`**：可选的自定义响应头，可用于传递错误码标识（如 `X-Error-Code`）或满足特定协议要求（如 401 需返回 `WWW-Authenticate`）。

下面演示参数校验失败返回 400、资源不存在返回 404 的常见用法：

```python
from fastapi import HTTPException, status

@app.get("/items/{item_id}")
def get_item(item_id: int):
    if item_id <= 0:
        # 400 Bad Request - 参数无效
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST,
            detail="item_id 必须为正整数",
            headers={"X-Error-Code": "INVALID_ID"}
        )

    item = fake_db.get(item_id)
    if item is None:
        # 404 Not Found - 资源不存在
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"ID 为 {item_id} 的条目不存在"
        )

    return item
```

> ### 🏗️ 项目实例：SyncHealth 自定义异常体系
>
> SyncHealth 将业务异常封装为继承 `HTTPException` 的类层级，让路由中抛出的异常自带正确的 HTTP 状态码：
>
> ```python
> # backend/app/core/exceptions.py - 业务异常类层级
> from fastapi import HTTPException, status
>
> class AppException(HTTPException):
>     """业务异常基类"""
>     def __init__(self, status_code: int, detail: str):
>         super().__init__(status_code=status_code, detail=detail)
>
> class NotFoundException(AppException):
>     """资源不存在 → 自动映射 404"""
>     def __init__(self, detail: str = "Resource not found"):
>         super().__init__(status_code=status.HTTP_404_NOT_FOUND, detail=detail)
>
> class UnauthorizedException(AppException):
>     """未授权 → 自动映射 401"""
>     def __init__(self, detail: str = "Unauthorized"):
>         super().__init__(status_code=status.HTTP_401_UNAUTHORIZED, detail=detail)
>
> class ConflictException(AppException):
>     """资源冲突 → 自动映射 409"""
>     def __init__(self, detail: str = "Resource already exists"):
>         super().__init__(status_code=status.HTTP_409_CONFLICT, detail=detail)
> ```
>
> 在 Service 层使用——业务逻辑只抛业务异常，不关心 HTTP：
>
> ```python
> # backend/app/services/auth_service.py - Service 层使用业务异常
> async def register_user(db, email, password, display_name):
>     result = await db.execute(select(User).where(User.email == email))
>     if result.scalar_one_or_none():
>         raise ConflictException("Email already registered")  # 自动 → 409
>     ...
>
> async def login_user(db, email, password):
>     user = result.scalar_one_or_none()
>     if not user or not verify_password(password, user.hashed_password):
>         raise UnauthorizedException("Invalid email or password")  # 自动 → 401
> ```

### 4.2 自定义异常处理器

`HTTPException` 虽然方便，但它有一个隐患：**它让业务逻辑和 Web 框架绑定在了一起**。

举个例子，假设你写了一个从数据库查询用户的函数：

```python
# 直接用 HTTPException —— 业务代码依赖了 FastAPI
from fastapi import HTTPException

def get_user_by_id(user_id: int):
    user = db.query(user_id)
    if not user:
        raise HTTPException(status_code=404, detail="用户不存在")  # 这是 HTTP 概念！
    return user
```

这个函数的目的是"查用户"，它不应该知道自己运行在 HTTP 环境里。后果是：

- **无法复用**：如果这个函数以后要被命令行脚本、定时任务、或者换一个 Web 框架（如 Flask）调用，`raise HTTPException(404)` 毫无意义——CLI 工具里根本没有"HTTP 状态码"这个概念，强行 raise 会报错。
- **测试尴尬**：单元测试本应只测"用户不存在时抛异常"这一个业务事实，但因为抛的是 `HTTPException`，测试代码必须去检查 `exc.status_code == 404`，把 HTTP 细节带进了业务测试。

**解决方案**：把"发生了什么业务错误"和"用哪个 HTTP 状态码响应"这两件事分开。业务代码只抛语义化的业务异常（如 `NotFoundException`），由一个集中的异常处理器负责把业务异常翻译成 HTTP 响应：

自定义异常处理器的优势：

- **关注点分离**：业务层只抛业务异常（如 `NotFoundException`、`ForbiddenException`），不关心 HTTP 状态码；异常处理器负责将业务异常映射为 HTTP 响应。
- **统一响应格式**：所有异常返回结构一致的 JSON（如 `{"success": False, "error": "...", "error_code": ...}`），前端只需一套逻辑处理错误。
- **异常继承体系**：定义 `BusinessException` 基类，派生出 `UnauthorizedException`（401）、`ForbiddenException`（403）、`NotFoundException`（404）等子类，只需为基类注册一个处理器即可统一处理所有子类异常。
- **状态码处理器**：除了异常类，还可以注册状态码处理器（如 `@app.exception_handler(404)`），自定义 404、500 等默认错误的响应格式。

下面演示完整的业务异常体系定义、全局处理器注册，以及在路由中的使用方式：

```python
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

# 自定义业务异常
class BusinessException(Exception):
    """业务异常基类"""
    def __init__(self, message: str, code: int = 400):
        self.message = message
        self.code = code

class UnauthorizedException(BusinessException):
    """未授权异常"""
    def __init__(self, message: str = "未授权"):
        super().__init__(message, code=401)

class ForbiddenException(BusinessException):
    """禁止访问异常"""
    def __init__(self, message: str = "无访问权限"):
        super().__init__(message, code=403)

class NotFoundException(BusinessException):
    """资源不存在异常"""
    def __init__(self, message: str = "资源不存在"):
        super().__init__(message, code=404)

# 注册全局异常处理器
@app.exception_handler(BusinessException)
async def business_exception_handler(request: Request, exc: BusinessException):
    """处理所有业务异常"""
    return JSONResponse(
        status_code=exc.code,
        content={
            "success": False,
            "error": exc.message,
            "error_code": exc.code
        }
    )

@app.exception_handler(404)
async def not_found_handler(request: Request, exc):
    """自定义 404 响应格式"""
    return JSONResponse(
        status_code=404,
        content={
            "success": False,
            "error": f"路径 {request.url.path} 不存在"
        }
    )

# 在路由中使用
@app.get("/admin/dashboard")
def admin_dashboard(current_user: str):
    if current_user != "admin":
        raise ForbiddenException("仅管理员可访问")
    return {"message": "管理员面板"}

@app.get("/items/v2/{item_id}")
def get_item_v2(item_id: int):
    if item_id <= 0:
        raise BusinessException("item_id 必须为正整数", code=400)
    item = fake_db.get(item_id)
    if item is None:
        raise NotFoundException(f"ID 为 {item_id} 的条目不存在")
    return item
```

### 4.3 全局异常捕获

即使已经处理了各类业务异常，仍可能存在预料之外的错误（如数据库连接断开、第三方服务超时、空指针异常等）。如果不做兜底处理，FastAPI 默认会返回 500 状态码和原始堆栈信息，既暴露服务器内部实现细节，又给前端提供不了有用的错误信息。

注册一个针对 `Exception` 基类的全局处理器可以解决这一问题：

- **兜底捕获**：`@app.exception_handler(Exception)` 会捕获所有未被其他处理器匹配的异常，作为最后一道防线。
- **隐藏内部细节**：返回给客户端的是统一的"服务器内部错误"提示，而非堆栈信息，避免泄露技术实现。
- **记录错误日志**：在处理器中调用 `traceback.print_exc()` 或写入日志系统，方便开发者排查问题。生产环境应使用 `logging` 而非 `print`。
- **返回请求上下文**：响应中可包含 `path` 等信息，帮助定位出错的接口。

下面演示全局异常处理器的实现：

```python
import traceback
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    """捕获所有未处理的异常，防止服务器崩溃"""
    # 生产环境应该记录日志而不是 print
    traceback.print_exc()
    return JSONResponse(
        status_code=500,
        content={
            "success": False,
            "error": "服务器内部错误，请稍后重试",
            "path": str(request.url.path)
        }
    )
```

### 4.4 错误处理最佳实践

在大型项目中，错误处理如果随意散落各处，会导致错误码不一致、响应格式混乱、前端难以统一处理。以下是推荐的实践方案：

- **使用枚举管理错误码**：将所有业务错误码（如 `USER_NOT_FOUND`、`INVALID_CREDENTIALS`）定义为 `Enum`，避免在代码中硬编码字符串。新增错误码只需在枚举中添加一项，便于维护和查找。
- **统一错误响应格式**：封装 `error_response()` 辅助函数，所有接口调用它抛出错误，保证响应结构一致（如 `{"code": "USER_NOT_FOUND", "message": "用户不存在"}`），前端只需一套逻辑解析错误。
- **错误码与状态码分离**：业务错误码（字符串枚举）表示具体的业务错误类型，HTTP 状态码表示 HTTP 层面的语义，两者配合使用。如 `USER_NOT_FOUND` 对应 404，`INVALID_CREDENTIALS` 对应 401。
- **错误信息对用户友好**：`detail` 应是用户可读的中文提示，而非技术性的英文报错。

下面演示用 `ErrorCode` 枚举定义错误码，并封装 `error_response` 辅助函数，在路由中直接调用即可抛出规范化的错误：

```python
# ✅ 推荐：使用枚举管理错误码
from enum import Enum

class ErrorCode(str, Enum):
    USER_NOT_FOUND = "USER_NOT_FOUND"
    USER_ALREADY_EXISTS = "USER_ALREADY_EXISTS"
    INVALID_CREDENTIALS = "INVALID_CREDENTIALS"
    INSUFFICIENT_PERMISSIONS = "INSUFFICIENT_PERMISSIONS"
    VALIDATION_ERROR = "VALIDATION_ERROR"

# ✅ 推荐：统一错误响应格式
def error_response(code: ErrorCode, detail: str, status_code: int = 400):
    raise HTTPException(
        status_code=status_code,
        detail={
            "code": code.value,
            "message": detail
        }
    )

@app.get("/users/{user_id}")
def get_user(user_id: int):
    user = fake_db.get(user_id)
    if not user:
        error_response(
            ErrorCode.USER_NOT_FOUND,
            f"用户 {user_id} 不存在",
            status_code=404
        )
    return user
```

## 5. 路径操作参数详解

### 5.1 Path() 路径参数校验

`Path()` 用于对 URL 路径中的动态参数施加约束和校验，功能与 `Field()` 类似，但专门用于路径参数（如 `/items/{item_id}` 中的 `item_id`）。

路径参数与查询参数的区别在于：路径参数是 URL 的一部分，必须有值（不能省略），因此 `Path()` 默认就是必填的。常见校验场景包括：

- **数值范围校验**：对 ID 类参数用 `ge`（最小值）、`le`（最大值）限制范围，如 `item_id` 必须 ≥ 1，避免负数或过大的 ID 查询数据库。
- **字符串格式校验**：对用户名等字符串参数用 `min_length`、`max_length`、`regex` 限制格式，如要求字母开头、只含字母数字下划线。
- **文档增强**：`title`、`description`、`example` 用于生成清晰的 OpenAPI 文档。

下面演示对数字 ID 的范围校验和对用户名的正则格式校验：

```python
from fastapi import Path

@app.get("/items/{item_id}")
def read_item(
    item_id: int = Path(
        ...,
        title="条目 ID",
        description="要获取的条目 ID",
        ge=1,                       # 大于等于 1
        le=1000000,                 # 小于等于 100 万
        example=42                  # 文档示例
    )
):
    return {"item_id": item_id}

# 使用正则约束路径参数
@app.get("/users/{username}")
def get_user(
    username: str = Path(
        min_length=3,
        max_length=20,
        regex=r"^[a-zA-Z][a-zA-Z0-9_]*$",  # 字母开头，字母数字下划线
        description="用户名，字母开头，可包含字母数字下划线"
    )
):
    return {"username": username}
```

### 5.2 Header() 请求头参数

HTTP 请求头常用于传递认证令牌（如 `Authorization`、`X-Token`）、客户端标识（如 `User-Agent`）、内容类型（如 `Content-Type`）等元信息。FastAPI 通过 `Header()` 自动解析请求头并注入到路由函数参数中。

`Header()` 的使用要点：

- **自动转换**：HTTP 请求头名不区分大小写，FastAPI 会自动处理。但请求头中的连字符（`-`）在 Python 变量名中不合法，因此需要用 `alias` 映射。
- **`alias` 参数**：将带连字符的请求头名映射为合法的 Python 变量名。例如 `x_token: str = Header(alias="X-Token")`，用 `x_token` 变量读取 `X-Token` 请求头。
- **可选默认值**：设为 `Header(None)` 表示该请求头可选，缺失时值为 `None`，不会报错。
- **自动转换下划线**：FastAPI 默认会将参数名中的下划线 `_` 转换为连字符 `-` 去匹配请求头，如 `user_agent` 会匹配 `User-Agent` 头。

下面演示读取 `User-Agent`、`X-Token` 等请求头：

```python
from fastapi import Header
from typing import Optional

@app.get("/client-info/")
def get_client_info(
    user_agent: Optional[str] = Header(None, description="浏览器 User-Agent"),
    x_token: Optional[str] = Header(None, alias="X-Token"),
    content_type: Optional[str] = Header(None)
):
    """
    读取自定义请求头
    alias="X-Token" 允许用 x_token 变量名读取 X-Token 请求头
    """
    return {
        "user_agent": user_agent,
        "token": x_token,
        "content_type": content_type
    }
```

### 5.3 Cookie() 读取 Cookie

Cookie 是浏览器存储在客户端的小段数据，每次请求会自动携带到服务器。常见的 Cookie 用途包括：会话标识（`session_id`，维持登录状态）、用户偏好（如主题、语言）、最近访问时间（`last_visit`，用于个性化推荐）、追踪标识（用于行为分析）。

FastAPI 通过 `Cookie()` 自动解析请求中的 Cookie 并注入到路由参数中：

- **声明方式**：`session_id: Optional[str] = Cookie(None)`，参数名即为 Cookie 名。
- **可选默认值**：设为 `Cookie(None)` 表示该 Cookie 可选，浏览器未携带时值为 `None`。
- **与 `alias` 配合**：如果 Cookie 名包含特殊字符，可用 `alias` 映射。
- **安全提示**：读取 Cookie 后应校验其有效性（如 session 是否过期、是否被篡改），不能盲目信任客户端数据。

下面演示读取 `session_id` 和 `last_visit` 两个 Cookie 值。

**注意：两行都写 `Cookie(None)`，但值一定不同。** 这里的 `Cookie(None)` 不是给变量赋一个固定值，而是告诉 FastAPI"这个参数的值请从 HTTP 请求的 Cookie 中读取，如果请求里没有这个 Cookie，才用 `None` 兜底"。`()` 里的 `None` 是**默认值**，括号外的 `Cookie` 是**数据来源标记**。

举个例子，当浏览器发送以下请求时：

```
GET /read-cookies/ HTTP/1.1
Cookie: session_id=abc123xyz; last_visit=2026-07-01
```

FastAPI 会解析 `Cookie` 头部，按参数名匹配：

- `session_id` 参数 → 找到名为 `session_id` 的 Cookie → 值 = `"abc123xyz"`
- `last_visit` 参数 → 找到名为 `last_visit` 的 Cookie → 值 = `"2026-07-01"`

两个参数都用 `Cookie(None)` 声明，只是表示"它们都从 Cookie 中读取，且都是可选的"，但实际读取的是**不同名称**的 Cookie，值自然不同：

```python
from fastapi import Cookie

@app.get("/read-cookies/")
def read_cookies(
    session_id: Optional[str] = Cookie(None),
    last_visit: Optional[str] = Cookie(None)
):
    return {
        "session_id": session_id,
        "last_visit": last_visit
    }
```

## 📝 第2阶段总结

### 核心知识点速查

| 概念 | 用途 | 关键代码 |
|------|------|----------|
| `Field()` | 字段级别校验 | `Field(gt=0, max_length=100)` |
| `@validator` | 自定义校验逻辑 | `@validator("field")` |
| `response_model` | 控制响应数据 | `response_model=UserResponse` |
| `status_code` | HTTP 状态码 | `status_code=201` |
| `UploadFile` | 文件上传 | `UploadFile = File(...)` |
| `Form()` | 表单数据 | `Form(...)` |
| `HTTPException` | 抛出 HTTP 错误 | `raise HTTPException(404)` |
| `@exception_handler` | 全局异常处理 | `@app.exception_handler(MyExc)` |
| `Path()` | 路径参数校验 | `Path(ge=1)` |
| `Query()` | 查询参数校验 | `Query(min_length=3)` |

### 最佳实践

1. **创建/读取/更新用不同模型** - `BookCreate` / `BookResponse` / `BookUpdate`
2. **始终用 `response_model`** - 避免泄露敏感字段（如密码哈希）
3. **文件上传要校验** - 类型、大小、扩展名都要检查
4. **统一错误格式** - 所有接口返回相同结构的错误响应
5. **使用 `BusinessException`** - 业务逻辑抛业务异常，与 HTTP 异常分离
