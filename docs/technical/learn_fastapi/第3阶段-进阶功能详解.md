## 1. 依赖注入 Depends

### 1.0 什么是依赖注入？

#### 一个真实的问题

假设你要写一个"查询当前用户的订单"接口。这个接口需要知道两件事：**当前是谁在访问**、**去哪里查数据**。

如果不用依赖注入，你会这样写：

```python
@app.get("/orders")
def get_orders():
    # 我得自己想办法拿到"当前用户"和"数据库连接"
    token = 从请求头解析...      # 每个接口都要写一遍
    user = 从 token 查出用户...   # 每个接口都要写一遍
    db = 创建数据库连接...        # 每个接口都要写一遍
    return db.query(Order).filter(Order.user_id == user.id).all()
```

这有什么问题？你有 20 个需要登录的接口，就要把"解析 token → 查用户 → 连数据库"这段逻辑复制 20 遍。哪天 token 格式改了，你得改 20 个地方。

#### 依赖注入怎么解决

用 `Depends()` 时，你不自己动手——你**在参数里声明你要什么**，FastAPI 帮你准备好：

```python
@app.get("/orders")
def get_orders(
    user = Depends(get_current_user),   # "我需要当前登录用户" → FastAPI 帮你去查
    db = Depends(get_db)               # "我需要数据库连接" → FastAPI 帮你创建
):
    # 直接拿到 user 和 db，不用管它们怎么来的
    return db.query(Order).filter(Order.user_id == user.id).all()
```

#### 对比：同一个效果，代码量差多少

```
❌ 没有依赖注入（每个接口都要写）：
   get_orders()   → 自己解析 token + 自己查用户 + 自己连数据库 + 业务逻辑
   get_profile()  → 自己解析 token + 自己查用户 + 自己连数据库 + 业务逻辑
   update_order() → 自己解析 token + 自己查用户 + 自己连数据库 + 业务逻辑
   ↑ "解析 token + 查用户 + 连数据库" 写了 3 遍

✅ 有依赖注入（只需声明）：
   get_orders(   user=Depends(get_current_user), db=Depends(get_db))
   get_profile(  user=Depends(get_current_user), db=Depends(get_db))
   update_order( user=Depends(get_current_user), db=Depends(get_db))
   ↑ get_current_user 和 get_db 各定义一次，到处可用
```

#### 一句话理解

**依赖注入 = "我要什么，在参数里写清楚就行，至于怎么来的，别问我，问框架。"**

**关于你的理解**：完全正确。`get_current_user` 和 `get_db` 也是你自己写的函数，里面的逻辑——查数据库、解析 token——一行都不会少写。区别只在于：你把这套逻辑**封装成一个独立函数**（只写一次），然后在 20 个接口里用 `Depends(get_current_user)` 引用它（不复制粘贴 20 遍）。

```
你写一次：                       你用 20 次（一行声明搞定）：
def get_current_user(...):       @app.get("/orders")
    token = 从请求头解析...        def get_orders(user = Depends(get_current_user)):
    user = 查数据库...                ...
    return user                      
                                @app.get("/profile")
                                def get_profile(user = Depends(get_current_user)):
                                    ...
```

`Depends()` 做的事就是：调用你写的 `get_current_user()`，拿到它 `return` 的值，然后塞给 `user` 参数。

#### 那为什么不直接调函数？用 `Depends()` 比手写函数调用多了什么？

你可能会想：既然 `get_current_user()` 就是个函数，我直接在路由函数里手动调它不就完了？

> 文档中说的"路由"或"路由函数"，就是指 `@app.get("/xxx")` 装饰器下面那个 `def` 函数——即处理某个 URL 请求的函数：
> ```python
> @app.get("/orders")           # ← 装饰器：声明 URL 路径和请求方法
> def get_orders():             # ← 这就是"路由函数"，也就是你写业务逻辑的地方
>     return {"data": ...}
> ```
> "路由参数"就是指 `def` 后面括号里的参数。之前学的 `Path()`、`Query()`、`Header()`、`Cookie()`、`Depends()` 全都是写在路由参数位置上的。




```python
# 为什么不能这样？
@app.get("/orders")
def get_orders():
    user = get_current_user()   # 直接调函数
    db = get_db()               # 直接调函数
    return db.query(Order).filter(Order.user_id == user.id).all()
```

不是不行，但你很快会遇到三个问题：

**问题 1：`get_current_user()` 自己也需要参数，这些参数谁来传？**

看一个真实的 `get_current_user` 长什么样：

```python
def get_current_user(token: str = Depends(oauth2_scheme), db = Depends(get_db)):
    """验证 token 并返回用户"""
    payload = verify_token(token)   # token 从哪来？→ 又是 Depends！
    user = db.query(User)...        # db 从哪来？  → 又是 Depends！
    return user
```

注意——`get_current_user` 它自己也声明了 `Depends(oauth2_scheme)` 和 `Depends(get_db)`！如果你手动调 `get_current_user()`，这些参数没人给你填——你得自己把 token 和 db 传进去。这就变成了：

```python
# 手动调的话，你得这样：
@app.get("/orders")
def get_orders():
    token = 从请求头解析...        # 回到了最初的噩梦
    db = 创建数据库连接...         # 又写了一遍
    user = get_current_user(token=token, db=db)   # 每个参数都要自己准备好
```

而 `Depends(get_current_user)` 呢？FastAPI 看到 `get_current_user` 自己也有 `Depends()`，会自动层层解开——先解 `oauth2_scheme` 拿到 token，再解 `get_db` 拿到 db，最后把这两个传给 `get_current_user`，拿到 user。你只需要一行声明。

**问题 2：资源清理谁负责？**

`get_db` 里的数据库连接用完之后必须关闭。如果你手动调 `get_db()`，你得自己在路由函数末尾写 `try/finally` 关闭它。而 `Depends(get_db)` 配合 `yield` 语法，FastAPI **保证一定在响应返回后执行清理代码**——哪怕中间抛了异常也不会泄露连接。

**问题 3：测试时怎么替换依赖？**

假设 `get_current_user` 正常流程是查数据库、验证 token。但写单元测试时，你不想真的连数据库，想用一个假用户代替。用 `Depends()` 的话，FastAPI 提供了 `app.dependency_overrides` 机制：

```python
# 测试中：一行代码把 get_current_user 替换成返回假用户的函数
def fake_user():
    return {"id": 99, "username": "测试用户"}

app.dependency_overrides[get_current_user] = fake_user

# 现在所有用了 Depends(get_current_user) 的接口
# 都不会真的执行 get_current_user，而是拿到 fake_user 的返回值
```

如果你是手动调用 `get_current_user()`，想替换它就得去源码里改，或者在每个路由函数里加 `if 测试模式:` 分支——侵入性极强。而 `Depends()` 让你在不改动任何路由代码的前提下完成替换。

**总结**：`Depends()` 本质上帮你做了三件手动调函数做不到或做起来很麻烦的事：

| | 手动调函数 | `Depends()` |
|--|-----------|-------------|
| 依赖嵌套（函数的参数也是依赖） | 你得一层层手动传参 | FastAPI 自动层层解开 |
| 资源清理（用完关闭） | 你手动写 `try/finally` | `yield` + `finally` 自动执行 |
| 测试时替换依赖 | 改源码或加 `if` 分支 | `dependency_overrides` 一行替换 |

这和之前学的 `Query()`、`Header()`、`Cookie()` 是同一套思路——只不过它们读的是 URL 参数或请求头，`Depends()` 读的是你自己定义的 Python 函数返回值。整个依赖系统像是可以无限嵌套的"俄罗斯套娃"：依赖函数本身也可以声明自己的 `Depends()`，一层套一层，FastAPI 会自动层层解开。

### 1.1 函数依赖（最常用）

一个普通的 Python 函数就可以作为依赖。当路由函数在参数中声明 `Depends(某函数)` 时，FastAPI 会在调用路由函数之前先执行该依赖函数，并将返回值注入到对应参数中。

依赖函数的返回值可以是任意类型（字典、Pydantic 模型、自定义对象等），它的参数本身也可以使用 `Query()`、`Header()` 等依赖——形成依赖嵌套。下面用 `common_parameters` 函数统一处理多个接口共享的查询参数 `q`、`skip`、`limit`，避免在每个接口中重复声明：

```python
from fastapi import FastAPI, Depends, Header, HTTPException
from typing import Optional

# === 定义依赖函数 ===

def common_parameters(
    q: Optional[str] = None,
    skip: int = 0,
    limit: int = 100
):
    """
    公共查询参数依赖
    多个接口共享相同的查询参数
    """
    return {"q": q, "skip": skip, "limit": limit}

# === 使用依赖 ===

@app.get("/items/")
def read_items(commons: dict = Depends(common_parameters)):
    """
    使用 common_parameters 依赖
    commons = common_parameters() 的返回值
    接口自动获得 q、skip、limit 三个查询参数
    """
    return commons

@app.get("/users/")
def read_users(commons: dict = Depends(common_parameters)):
    """另一个接口复用同一个依赖"""
    return {"users": [], **commons}
```

> ### 🏗️ 项目实例：SyncHealth 数据库会话依赖 (yield 模式)
>
> SyncHealth 最核心的依赖是 `get_db`——用 `yield` 模式在每个请求中创建异步数据库会话，请求结束后自动 commit 或 rollback：
>
> ```python
> # backend/app/database.py - 数据库会话依赖（yield 资源管理）
> from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
>
> engine = create_async_engine(settings.DATABASE_URL, echo=settings.DEBUG)
> async_session_factory = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
>
> async def get_db():
>     async with async_session_factory() as session:
>         try:
>             yield session            # 注入到路由函数
>             await session.commit()   # 请求成功 → 提交
>         except Exception:
>             await session.rollback()  # 请求失败 → 回滚
>             raise
>     # 离开 async with 块时自动关闭 session
> ```
>
> 所有路由函数中通过 `db: AsyncSession = Depends(get_db)` 一行声明即可获得数据库会话，无需手动管理连接和事务。
>
> ---
>
> #### 逐行解读：`yield session` → `commit()` → `rollback()` 到底在干什么
>
> 上面的 `get_db()` 是 1.4 节才会讲的 `yield` 模式，这里先逐行拆解，让你能看懂项目代码。
>
> **① `yield session`：暂停 + 传值 + 等待**
>
> Python 中 `yield` 把普通函数变成"能暂停、能恢复"的生成器。FastAPI 内部大致这样执行：
>
> ```
> FastAPI 收到请求
>   → 发现 db 参数声明了 Depends(get_db)
>   → 调用 get_db()，得到生成器对象
>   → next(gen) 执行到 yield session → 拿到 session
>   → 把 session 赋值给路由函数的 db 参数
>   → 执行路由函数：db.execute(...)、db.add(...) 等
>   → 路由函数返回 → next(gen) 继续执行 yield 后面的代码
> ```
>
> 普通 `return` 是"一次性的"，给完就结束；`yield` 是"你先用，我在这里等着，用完叫我"。
>
> **② `await session.commit()`：把数据真正写入磁盘**
>
> `db.add(book)` 只是把数据暂存在内存，`commit()` 才执行 `INSERT` SQL 写入硬盘：
>
> ```
> 路由函数中：db.add(book)    → 数据在内存，book.id 为 None
> yield 之后：await commit()  → INSERT INTO books ... 写入磁盘，book.id 在数据库生成
> ```
>
> 放在 `yield` 后面是因为：必须等路由函数全部操作完，才能确定"要写入什么"。
>
> > **GET 请求不会修改数据，`commit()` 是不是多此一举？**
> >
> > 在纯查询（GET）接口上，没有任何待提交的变更，`commit()` 是空操作，立刻通过，无副作用。
> > `get_db` 被所有路由共享（GET/POST/PUT/DELETE 都用它），没必要为只读接口单独写一份。多一行 `commit()` 没有性能损失，但保证写入类接口的数据不会忘记提交。
>
> **③ `await session.rollback()`：撤销本次会话的所有修改**
>
> 当路由函数中抛异常时，`except` 捕获后执行 `rollback()`——把这次会话里的所有 `add`、`delete`、修改全部撤销，数据库状态回到请求进来之前：
>
> ```python
> # 假设路由函数中发生了异常
> @router.post("/register")
> async def register(data, db = Depends(get_db)):
>     db.add(user)                       # 加入内存
>     send_welcome_email(data.email)     # 💥 这里抛异常！
>     return {"message": "注册成功"}      # 不会执行
>
> # get_db 的流程：
> # yield session → 路由函数异常 → except 捕获
> # → await session.rollback() → 撤销 db.add(user)
> # → user 不会写入数据库，数据保持干净
> ```
>
> 没有 `rollback()` 的话，异常后的 session 处于"脏状态"——有未提交的修改残留，下一个请求复用这个连接可能拿到脏数据。
>
> **总结一图**：
>
> ```
> 请求进来
>    ↓
> 创建 session
>    ↓
> yield session  ← 暂停！把 session 给路由函数
>    ↓               ↓
> 等待...        路由函数执行（查数据 / 增删改）
>    ↓               ↓
>  ←──────── 路由函数结束
>    ↓
> ┌─ 正常？ → await commit()    → 写入数据库
> └─ 异常？ → await rollback()  → 全部撤销
>    ↓
> 关闭 session
> ```

### 1.2 类依赖

除了函数，类也可以作为依赖。当路由参数声明类型为某个类且配合 `Depends()`（不带参数）时，FastAPI 会自动实例化这个类，并调用 `__init__` 方法。

类依赖的优势在于：可以在构造函数中加入业务逻辑（如对传入参数进行计算或限制），还可以通过 `@property` 提供计算属性（如分页的 `offset`）。与函数依赖不同，类依赖注入的是实例对象本身，而不是函数的返回值。下面用 `PaginationParams` 类封装分页参数，并在初始化时限制最大页大小，同时提供 `offset` 计算属性：

```python
class PaginationParams:
    """分页参数依赖（类方式）"""
    def __init__(
        self,
        page: int = 1,
        page_size: int = 20,
        max_page_size: int = 100
    ):
        self.page = page
        self.page_size = min(page_size, max_page_size)  # 限制最大页大小

    @property
    def offset(self) -> int:
        """计算偏移量"""
        return (self.page - 1) * self.page_size

@app.get("/articles/")
def list_articles(pagination: PaginationParams = Depends()):
    """
    使用类依赖时，Depends() 不需要参数
    FastAPI 自动调用 PaginationParams 的 __init__
    """
    return {
        "page": pagination.page,
        "page_size": pagination.page_size,
        "offset": pagination.offset,
        "articles": [f"Article {pagination.offset + i}"
                      for i in range(pagination.page_size)]
    }
```

### 1.3 子依赖（依赖链）

依赖可以嵌套，形成依赖链——`A 用 Depends(B)`、`B 用 Depends(C)`，FastAPI 会自动按层级从最底层开始依次解析。这种模式在认证授权场景中特别有用：`Header → 提取 token → 解析用户 → 校验权限`，每一层只做一件事，逻辑清晰、可复用。

> ### 🏗️ 项目实例：SyncHealth 认证依赖链
>
> SyncHealth 的 `get_current_user` 是典型的二级依赖链：`HTTPBearer（提取 Authorization 头）→ get_current_user（验证 token → 查数据库 → 返回 User）`。全国所有需要登录的接口只需声明 `Depends(get_current_user)` 即可获得当前用户：
>
> ```python
> # backend/app/core/dependencies.py - 认证依赖链
> from fastapi import Depends, HTTPException, status
> from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer
>
> security_scheme = HTTPBearer()  # 第1层：从请求头提取 Bearer token
>
> async def get_current_user(
>     credentials: HTTPAuthorizationCredentials = Depends(security_scheme),  # → 第1层
>     db: AsyncSession = Depends(get_db),                                    # → 数据库依赖
> ) -> User:
>     """
>     第2层：验证 token → 解析用户 ID → 查数据库 → 返回 User 对象
>     依赖链：security_scheme → get_current_user → 路由函数
>     """
>     token = credentials.credentials
>     try:
>         payload = decode_token(token)
>     except Exception:
>         raise HTTPException(status_code=401, detail="Invalid or expired token")
>
>     if payload.get("type") != "access":
>         raise HTTPException(status_code=401, detail="Invalid token type")
>
>     user_id: int = payload.get("sub")
>     if user_id is None:
>         raise HTTPException(status_code=401, detail="Invalid token")
>
>     result = await db.execute(select(User).where(User.id == user_id))
>     user = result.scalar_one_or_none()
>     if user is None:
>         raise HTTPException(status_code=401, detail="User not found")
>     return user
> ```
>
> 在健康数据查询端点中，`get_current_user` 和 `get_db` 同时注入，无需任何认证代码：
>
> ```python
> # backend/app/api/health.py - 两个依赖同时注入
> @router.get("/heart-rate")
> async def get_heart_rates(
>     page: int = Query(1, ge=1),
>     current_user: User = Depends(get_current_user),  # 认证依赖
>     db: AsyncSession = Depends(get_db),               # 数据库依赖
> ):
>     items, total = await query_heart_rates(db, current_user.id, ...)
>     return _paginate(items, total, page, page_size, HeartRateOut)
> ```
>
> 以上展示了 `Depends` 最强大的特性：**多层依赖链**（`HTTPBearer → get_current_user → 路由`）和**多依赖组合注入**（`current_user` + `db` 同时注入）。

下面演示一个三级依赖链：`get_token`（从请求头提取 token）→ `get_current_user`（验证 token 并返回用户）→ `require_admin`（检查管理员权限）。`/me` 只需要前两级，`/admin` 则需要完整的三级：

```python
from fastapi import Depends, HTTPException

# 子依赖 1：获取请求头中的 token
def get_token(authorization: Optional[str] = Header(None)):
    if not authorization:
        raise HTTPException(status_code=401, detail="缺少认证令牌")
    # 格式: "Bearer <token>"
    scheme, _, token = authorization.partition(" ")
    if scheme.lower() != "bearer":
        raise HTTPException(status_code=401, detail="认证格式错误")
    return token

# 子依赖 2：从 token 解析用户信息
def get_current_user(token: str = Depends(get_token)):
    """
    依赖注入链：get_current_user → 依赖 get_token → 依赖 Header
    FastAPI 自动按顺序解析
    """
    if token == "admin-token":
        return {"id": 1, "username": "admin", "role": "admin"}
    elif token == "user-token":
        return {"id": 2, "username": "user", "role": "user"}
    else:
        raise HTTPException(status_code=401, detail="无效的令牌")

# 子依赖 3：权限校验
def require_admin(user: dict = Depends(get_current_user)):
    """只有管理员能通过"""
    if user.get("role") != "admin":
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return user

# 使用依赖
@app.get("/me")
def read_current_user(user: dict = Depends(get_current_user)):
    """获取当前用户信息（不需要管理员）"""
    return {"user": user}

@app.get("/admin")
def admin_panel(admin: dict = Depends(require_admin)):
    """管理员面板（需要管理员权限）"""
    return {"message": "欢迎来到管理员面板", "admin": admin}

# 依赖链可视化：
# /me:        Header → get_token → get_current_user → read_current_user
# /admin:     Header → get_token → get_current_user → require_admin → admin_panel
```

### 1.4 带 yield 的依赖（资源管理）

前面的依赖都是"一次性"的——执行完就结束了。但有些资源（数据库连接、文件句柄、网络连接）用完后必须关闭释放。FastAPI 支持在依赖函数中使用 `yield`，实现类似 Python 上下文管理器（`with` 语句）的效果。

`yield` 依赖的执行流程分为三个阶段：
1. **请求前**：`yield` 之前的代码执行，准备资源（如打开数据库连接）。
2. **请求中**：`yield` 后面的值被注入到路由函数中作为依赖值。
3. **请求后**：路由函数执行完毕、响应返回后，`yield` 之后的代码执行（写在 `finally` 块中可确保异常时也能清理）。

下面用数据库连接的例子演示：`get_db` 在请求前打开连接、`yield` 注入会话、请求结束后自动关闭连接：

```python
from contextlib import contextmanager

# 模拟数据库会话
class DBSession:
    def __init__(self):
        self.connected = False

    def connect(self):
        print("📂 数据库连接已打开")
        self.connected = True
        return self

    def close(self):
        print("📂 数据库连接已关闭")
        self.connected = False

    def query(self, sql: str):
        if not self.connected:
            raise RuntimeError("数据库未连接")
        print(f"执行查询: {sql}")
        return [{"id": 1, "name": "测试数据"}]

def get_db():
    """
    yield 依赖的工作流程：
    1. yield 之前的代码 → 请求处理前执行
    2. yield db → 将 db 注入到路由函数
    3. yield 之后的代码 → 响应返回后执行（清理资源）
    """
    session = DBSession()
    try:
        db = session.connect()
        yield db  # 把 db 传给路由函数
    finally:
        # 无论请求成功还是失败，都会执行清理
        session.close()

@app.get("/data")
def read_data(db: DBSession = Depends(get_db)):
    return db.query("SELECT * FROM items")
```

### 1.5 依赖参数缓存

当同一个请求中多个路由参数声明了相同的依赖（如 `db1 = Depends(get_db)` 和 `db2 = Depends(get_db)`），FastAPI 默认只会执行一次依赖函数，然后将结果缓存并复用于所有参数——这叫"同级缓存"。

缓存的含义是：**同一个请求内、同一次调用中**，同一个依赖函数不会重复执行。这避免了不必要的重复工作（如重复创建数据库连接）。如果你确实需要每次都创建新的实例（如需要独立的临时对象），可以设置 `use_cache=False` 禁用缓存。下面分别演示两种模式：

```python
def get_db_session():
    print("创建数据库会话")  # 每个请求只打印一次
    return {"session": "new"}

@app.get("/cached")
def cached(
    db1: dict = Depends(get_db_session),
    db2: dict = Depends(get_db_session)
):
    """db1 和 db2 是同一个对象（缓存）"""
    return {"same": db1 is db2}  # True

@app.get("/no-cache")
def no_cache(
    db1: dict = Depends(get_db_session, use_cache=False),
    db2: dict = Depends(get_db_session, use_cache=False)
):
    """db1 和 db2 是不同的对象（不使用缓存）"""
    print("创建了两次")  # 会打印两次
    return {"same": db1 is db2}  # False
```

## 2. 中间件与 CORS

### 2.0 什么是中间件？

中间件是请求处理的"过滤器链"，每个请求都要经过中间件：

```
请求 → 中间件1 → 中间件2 → ... → 路由处理函数 → ... → 中间件2 → 中间件1 → 响应
```

**常见用途**：
- 请求日志记录
- CORS 跨域处理
- 请求限流
- 请求计时
- 统一响应格式化

### 2.1 基本中间件

FastAPI 提供了两种编写中间件的方式：装饰器风格（`@app.middleware("http")`）和类方式（继承 `BaseHTTPMiddleware`）。

**装饰器风格**适合简单的逻辑，核心是两个要素：`request`（请求对象）和 `call_next`（一个可调用对象，代表"交棒给下一个中间件或最终的路由函数"）。`await call_next(request)` 就像传球——把请求传下去处理，拿到响应后再传回来，你可以分别在传下去之前和传回来之后做事情。

**类方式**通过重写 `dispatch` 方法实现，代码结构更清晰，适合复杂中间件（如全链路日志、请求限流），也方便通过 `app.add_middleware()` 注册。

下面先用装饰器风格实现请求计时中间件，再用类方式实现请求日志中间件：

```python
import time
from fastapi import FastAPI, Request
from starlette.middleware.base import BaseHTTPMiddleware

# === 方式1：装饰器风格（简单） ===
@app.middleware("http")
async def add_process_time_header(request: Request, call_next):
    """
    最简单的中间件：计算请求处理时间
    call_next = 下一个中间件或路由处理函数
    """
    start_time = time.time()
    # 执行前：可以修改 request
    response = await call_next(request)  # 调用下一个处理环节
    # 执行后：可以修改 response
    process_time = time.time() - start_time
    response.headers["X-Process-Time"] = f"{process_time:.4f}s"
    return response

# === 方式2：类方式（更结构化的中间件） ===
class RequestLogMiddleware(BaseHTTPMiddleware):
    """请求日志中间件"""

    async def dispatch(self, request: Request, call_next):
        # 请求前
        print(f"→ {request.method} {request.url.path}")

        # 执行请求
        response = await call_next(request)

        # 请求后
        print(f"← {response.status_code}")
        return response

app.add_middleware(RequestLogMiddleware)
```

### 2.2 CORS 跨域配置

前后端分离项目中，前端（`localhost:3000`）和后端（`localhost:8000`）虽然 IP 相同，但端口不同，浏览器视为"不同源"（Origin）。默认情况下浏览器禁止跨域请求，后端必须通过 CORS（跨域资源共享）响应头明确告诉浏览器"允许来自哪些地址的请求"。

> ### 🏗️ 项目实例：SyncHealth CORS 配置
>
> SyncHealth 在 `create_app()` 中配置 CORS，通过 `pydantic-settings` 管理来源白名单：
>
> ```python
> # backend/app/main.py - CORS 配置
> from fastapi.middleware.cors import CORSMiddleware
>
> def create_app() -> FastAPI:
>     app = FastAPI(title="SyncHealth", version="0.1.0", lifespan=lifespan)
>
>     app.add_middleware(
>         CORSMiddleware,
>         allow_origins=settings.CORS_ORIGINS,  # 从配置读取白名单
>         allow_credentials=True,
>         allow_methods=["*"],
>         allow_headers=["*"],
>     )
>     ...
>
> # backend/app/config.py - CORS 白名单配置
> class Settings(BaseSettings):
>     CORS_ORIGINS: list[str] = [
>         "http://localhost:5173",   # Vite
>         "http://localhost:3000",   # React
>         "http://localhost:3001",
>         "http://localhost:8081",
>         "http://localhost:8082",
>     ]
> ```

CORS 的三个核心概念：
- **Origin（来源）**：协议 + 域名 + 端口，如 `http://localhost:3000`，三个中任一不同即"跨域"。
- **Credentials（凭证）**：`allow_credentials=True` 允许浏览器携带 Cookie、Authorization 头等凭据。注意此时 `allow_origins` 必须指定具体域名，不能用 `*`。
- **Preflight（预检请求）**：对于非简单请求（如 `Content-Type: application/json` 的 POST），浏览器会先发一个 `OPTIONS` 请求"探路"，服务器返回允许的配置后浏览器才发真正的请求。`max_age` 可以缓存预检结果，减少重复 OPTIONS 请求。

下面演示完整的 CORS 配置，包含开发和生产环境的来源白名单：

```python
from fastapi.middleware.cors import CORSMiddleware

# 配置 CORS
app.add_middleware(
    CORSMiddleware,
    # 允许的来源（前端地址）
    allow_origins=[
        "http://localhost:3000",      # React 开发服务器
        "http://localhost:5173",      # Vite 开发服务器
        "https://your-domain.com"     # 生产环境
    ],
    # 生产环境建议用 allow_origin_regex 代替（更灵活）

    allow_credentials=True,   # 允许携带 Cookie
    allow_methods=["*"],      # 允许所有 HTTP 方法
    allow_headers=["*"],      # 允许所有请求头
    expose_headers=["X-Process-Time"],  # 允许前端读取的响应头
    max_age=3600             # 预检请求缓存时间（秒）
)

# CORS 三个核心概念：
# 1. Origin（来源）          - 请求从哪个域名发出
# 2. Credentials（凭证）     - 是否携带 Cookie/Authorization
# 3. Preflight（预检请求）    - 复杂请求先发 OPTIONS 确认
```

**简化版本（开发环境）**：

```python
# 开发时允许所有来源（生产环境不要这样用！）
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],       # 开发环境允许所有
    allow_methods=["*"],
    allow_headers=["*"],
)
```

### 2.3 中间件实战：全链路日志

在微服务或复杂系统中，一个请求可能经过多个服务和中间件，排查问题需要"全链路追踪"——给每个请求生成一个唯一 ID，从进入到离开全程记录日志，便于通过 ID 串联所有相关记录。

这个示例用一个 `TraceMiddleware` 类实现四个功能：
1. 为每个请求生成 8 位唯一 `request_id`，存在 `request.state` 中供后续使用。
2. 请求开始时记录方法和路径。
3. 请求结束时记录状态码和耗时；如果发生异常，记录异常类型和信息。
4. 将 `request_id` 写入响应头 `X-Request-ID`，前端配合可快速定位问题请求。

```python
import uuid
import time
import logging
from starlette.middleware.base import BaseHTTPMiddleware

# 配置日志
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("api")

class TraceMiddleware(BaseHTTPMiddleware):
    """全链路追踪中间件"""

    async def dispatch(self, request: Request, call_next):
        # 生成唯一请求 ID
        request_id = str(uuid.uuid4())[:8]
        request.state.request_id = request_id

        # 记录请求开始
        start_time = time.time()
        logger.info(
            f"[{request_id}] → {request.method} {request.url.path}"
            f" | Query: {dict(request.query_params)}"
        )

        # 执行请求
        try:
            response = await call_next(request)
            elapsed = time.time() - start_time
            logger.info(
                f"[{request_id}] ← {response.status_code} "
                f"| Time: {elapsed:.3f}s"
            )
        except Exception as e:
            elapsed = time.time() - start_time
            logger.error(
                f"[{request_id}] ✕ {type(e).__name__}: {e} "
                f"| Time: {elapsed:.3f}s"
            )
            raise

        # 添加追踪 ID 到响应头
        response.headers["X-Request-ID"] = request_id
        return response

app.add_middleware(TraceMiddleware)
```

## 3. 后台任务 BackgroundTasks

### 3.1 基本用法

`BackgroundTasks` 是 FastAPI 内置的轻量级后台任务机制。它的核心思路是：**先把响应返回给客户端，再在后台慢慢执行耗时操作**——用户不用等邮件发完才收到"注册成功"的响应。

`BackgroundTasks` 的工作流程：
1. 路由函数中调用 `background_tasks.add_task(函数名, 参数1, 参数2, ...)` 注册任务。
2. 路由函数正常 `return` 响应给客户端。
3. FastAPI 在响应发送后才执行所有注册的后台任务。

需要注意的是：后台任务**不能修改已返回的响应内容**（响应已经发出了），因此不适合需要返回处理结果的场景。它最适合的场景是"发通知"类操作（邮件、短信、日志、推送），需要更复杂任务保障的请用 Celery 等消息队列。下面以用户注册后发送欢迎邮件和写日志为例：

```python
from fastapi import BackgroundTasks

def send_email(to: str, subject: str, body: str):
    """模拟发送邮件（耗时操作）"""
    import time
    print(f"📧 正在发送邮件到 {to}...")
    time.sleep(3)  # 模拟发送耗时
    print(f"📧 邮件已发送到 {to}！主题: {subject}")

def write_log(message: str):
    """写入日志文件"""
    with open("app.log", "a", encoding="utf-8") as f:
        f.write(f"{message}\n")

@app.post("/register/")
async def register(email: str, background_tasks: BackgroundTasks):
    """
    用户注册后，立即返回"注册成功"
    邮件发送在后台执行，不阻塞响应
    """
    # 添加后台任务
    background_tasks.add_task(
        send_email,
        email,
        "注册成功",
        "欢迎注册我们的服务！"
    )
    background_tasks.add_task(
        write_log,
        f"新用户注册: {email}"
    )

    # 立即返回，后台任务在响应之后执行
    return {"message": "注册成功，确认邮件正在发送"}
```

> ### 🏗️ 项目实例：SyncHealth Apple Health 导入后台任务
>
> 用户上传 Apple Health 导出文件 → 立即返回 `task_id` → 后台解析 ZIP/XML → 批量写入数据库。任务状态存储在内存中，可通过 `/status/{task_id}` 查询进度：
>
> ```python
> # backend/app/api/apple_health.py - BackgroundTasks 实战
> from fastapi import BackgroundTasks
>
> @router.post("/upload")
> async def upload_apple_health(
>     background_tasks: BackgroundTasks,
>     file: UploadFile = File(...),
>     current_user: User = Depends(get_current_user),
> ):
>     # ... 保存文件 ...
>     _import_tasks[task_id] = {"task_id": task_id, "status": "pending", ...}
>
>     # 关键：add_task 注册后台函数，响应先返回，后台再执行
>     background_tasks.add_task(_run_import_task, task_id, save_path, current_user.id)
>
>     return {"task_id": task_id, "status": "pending"}  # 立即返回，不等后台完成
> ```
>
> 后台任务 `_run_import_task` 在独立上下文中流式解析 XML、分批写入数据库、更新进度状态，用户可通过轮询 `/status/{task_id}` 获取实时进度。

### 3.2 适用于后台任务的场景

| 场景 | 示例 |
|------|------|
| 发送邮件 | 注册确认、密码重置、通知 |
| 发送短信 | 验证码、营销通知 |
| 数据统计 | 更新访问计数、统计报表 |
| 日志记录 | 操作日志、审计日志 |
| 清理工作 | 删除临时文件、过期数据 |
| 第三方推送 | Webhook 通知、消息推送 |

### 3.3 不适合后台任务的情况

- 需要返回处理结果的（用异步轮询或 WebSocket）
- 需要保证一定成功的（用消息队列如 Celery）
- 非常耗时的计算任务（用 Celery）
- 需要在多服务器间协调的（用 Redis + Celery）

## 4. SQLAlchemy 数据库集成

### 4.0 概念理解：SQLAlchemy 是什么？为什么需要它？

#### 4.0.1 原始 SQL vs ORM

操作数据库有两种方式：

**方式一：手写原始 SQL（传统方式）**

```python
# 需要自己拼接 SQL 字符串，容易出错
cursor.execute("SELECT * FROM books WHERE title LIKE '%" + keyword + "%'")
# ↑ 如果 keyword 包含恶意字符 → SQL 注入漏洞！

cursor.execute("INSERT INTO books (title, author, price) VALUES (?, ?, ?)",
               [title, author, price])
# 字段多了容易写错顺序
```

**方式二：使用 ORM（SQLAlchemy 的方式）**

ORM = Object Relational Mapping，对象关系映射
```python
# 操作 Python 对象 = 操作数据库，SQLAlchemy 自动生成安全 SQL
book = Book(title="三体", author="刘慈欣", price=39.9)  # 创建 Python 对象
db.add(book)                                           # 等价于 INSERT
db.commit()                                            # 提交到数据库

books = db.query(Book).filter(Book.price > 30).all()   # 等价于 SELECT
# SQLAlchemy 自动生成: SELECT * FROM books WHERE price > 30
```

**ORM (Object-Relational Mapping)** 的核心思想：**用操作 Python 对象的方式操作数据库**。

```
Python 对象          ←→  数据库表
───────────────────────────────
class Book            ←→  books 表
book.title = "三体"   ←→  title 列的值是 "三体"
db.add(book)          ←→  INSERT INTO books ...
db.query(Book)        ←→  SELECT * FROM books ...
```

**ORM 的好处**：
| 问题 | 手写 SQL | ORM |
|------|----------|-----|
| SQL 注入 | 需要手动防范 | 自动使用参数化查询，安全 |
| 字段名拼写错误 | 运行时报错 | IDE 自动补全，写错就有红线 |
| 数据库切换 | 重写 SQL 方言 | 改一行配置即可 |
| 代码可读性 | SQL 字符串嵌在 Python 里 | 链式调用，接近自然语言 |

---

#### 4.0.2 SQLAlchemy 的三个核心组件

使用 SQLAlchemy 需要理解三个角色，它们分工协作：

```
┌──────────────────────────────────────────────────────────┐
│                    SQLAlchemy 架构                         │
│                                                          │
│  ┌────────────────┐                                      │
│  │    Engine       │  引擎：负责和数据库建立连接           │
│  │  (发动机)       │  线程池、连接池管理                   │
│  └───────┬────────┘                                      │
│          │ 提供连接                                        │
│          ▼                                                │
│  ┌────────────────┐                                      │
│  │   Session       │  会话：你和数据库之间的"对话"          │
│  │  (对话窗口)     │  add/commit/query 都在会话上进行       │
│  │                 │  可以理解为"一次数据库操作的事务"       │
│  └───────┬────────┘                                      │
│          │ 操作对象                                        │
│          ▼                                                │
│  ┌────────────────┐                                      │
│  │    Model        │  模型：Python 类 = 数据库表            │
│  │  (映射表)       │  class Book → books 表               │
│  │                 │  book.title → title 列               │
│  └────────────────┘                                      │
└──────────────────────────────────────────────────────────┘
```

**通俗理解**：

| 组件 | 角色 | 比喻 |
|------|------|------|
| **Engine** | 连接数据库 | 银行的金库大门——进出都要经过它 |
| **Session** | 执行操作 | 你在银行柜台办业务——存钱、取钱、查余额 |
| **Model** | 数据映射 | 你的银行卡——卡号→数据库行，余额→列值 |

> **关键理解**：`Engine` 是全局只创建一次的（和数据库的长连接），`Session` 是每个请求创建一个新的（一次业务操作），`Model` 是你定义的 Python 类（表结构）。

### 4.1 数据库连接配置（database.py）

先看完整代码，再逐块解释：

```python
# database.py - 数据库配置与连接管理

from sqlalchemy import create_engine
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.orm import sessionmaker, Session
from typing import Generator

# 数据库 URL 格式：<数据库类型>:///<文件路径>
SQLALCHEMY_DATABASE_URL = "sqlite:///./book.db"

# 创建引擎
# connect_args 是 SQLite 特有参数（其他数据库不需要）
engine = create_engine(
    SQLALCHEMY_DATABASE_URL,
    connect_args={"check_same_thread": False},  # SQLite 需要
    echo=True  # 打印 SQL 语句（调试用）
)

# 创建会话工厂
SessionLocal = sessionmaker(
    autocommit=False,
    autoflush=False,
    bind=engine
)

# 模型基类
Base = declarative_base()

# 依赖注入：获取数据库会话
def get_db() -> Generator[Session, None, None]:
    """
    每个请求获取一个数据库会话，请求结束自动关闭
    使用 yield 确保异常时也能关闭
    """
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

> ### 🏗️ 项目实例：SyncHealth 异步 SQLAlchemy 配置
>
> SyncHealth 使用 **异步 SQLAlchemy**（`create_async_engine` + `aiosqlite`），支持 FastAPI 的 `async/await` 全链路异步。`get_db` 用 `async with` + `try/yield` 管理事务生命周期，请求成功自动 commit、失败自动 rollback：
>
> ```python
> # backend/app/database.py - 异步数据库配置（完整版）
> from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine
> from sqlalchemy.orm import DeclarativeBase
>
> engine = create_async_engine(settings.DATABASE_URL, echo=settings.DEBUG)
> async_session_factory = async_sessionmaker(engine, class_=AsyncSession, expire_on_commit=False)
>
> class Base(DeclarativeBase):
>     pass
>
> async def get_db():
>     async with async_session_factory() as session:
>         try:
>             yield session
>             await session.commit()    # 自动提交
>         except Exception:
>             await session.rollback()   # 自动回滚
>             raise
>
> async def init_db():
>     async with engine.begin() as conn:
>         try:
>             await conn.run_sync(Base.metadata.create_all)  # 自动建表
>         except OperationalError:
>             pass  # 并发启动时忽略 "already exists"
>         await _run_migrations(conn)  # 执行 ALTER TABLE 迁移
> ```
>
> 数据库 URL 由 `pydantic-settings` 管理：`sqlite+aiosqlite:///{项目根}/data/synchealth.db`。关键差异在于：文档示例是同步方案（`create_engine` + `sessionmaker`），而 SyncHealth 是**异步方案**（`create_async_engine` + `async_sessionmaker`），更适合 FastAPI 的 async 路由。

#### 逐行详解

**① `create_engine()` — 创建数据库引擎**

```python
engine = create_engine("sqlite:///./book.db", echo=True)
#                                  ↑              ↑
#                          数据库 URL      echo=True = 打印每条 SQL
```

`Engine` 是 SQLAlchemy 最底层的对象，负责：
- 管理数据库连接池
- 将 SQLAlchemy 的查询翻译成具体数据库的 SQL 方言
- 执行 SQL 语句

`echo=True` 会在终端打印每一次实际执行的 SQL，**强烈建议开发阶段开启**，能直观看到 ORM 生成了什么 SQL。

**② `sessionmaker()` — 创建会话工厂**

```python
SessionLocal = sessionmaker(
    autocommit=False,    # 不自动提交——需要手动 db.commit()
    autoflush=False,     # 不自动刷新——在 commit 时才同步到数据库
    bind=engine          # 绑定到前面创建的引擎
)
```

`sessionmaker` 是一个**工厂函数**，返回一个用来生产 Session 的"模具"。每次调用 `SessionLocal()` 都会产出一个全新的 Session。

**工厂函数和类的关系**：你说得对，用类实例化对象本身就像"工厂生产产品"。但 `sessionmaker` 做的事更复杂一步——它不是一个普通的类，它的产物也不是某个类的实例，而是一个**已经被预配置好的"可调用对象"**。

用三层类比来理解：

```
普通类（你自己写的）：
  定义 class Car: →  Car() → 生产一辆车
                      ↑ 模具（类）   ↑ 产品（实例）

工厂函数（sessionmaker）：
  sessionmaker(配置参数) → SessionLocal → SessionLocal() → 生产一个 Session
         ↑                      ↑                ↑
    模具制造机            定制好的模具         产品（实例）
```

关键差异：普通类 `class Car` 的配置是写死的（在 `__init__` 里），而 `sessionmaker(autocommit=False, bind=engine)` 可以让你**运行时动态配置**模具——给不同的项目生产不同配置的"Session 模具"。如果你用普通类，就得提前把所有配置写死在 `__init__` 里。

**为什么叫 `SessionLocal`？** 这是个命名惯例——每个请求调用一次 `SessionLocal()`，得到独立的数据库会话，互不干扰。

```
请求1 到来 → db1 = SessionLocal() → 查书、买书 → db1.close()
请求2 到来 → db2 = SessionLocal() → 查用户 → db2.close()
             ↑ 两个 Session 完全独立
```

**③ `declarative_base()` — 创建模型基类**

```python
Base = declarative_base()
```

这一行代码返回的 `Base` 本质上就是一个 Python 类。你可以把它的"长相"理解为：

```python
# 不用看源码，这是 Base 内部的简化版——它自带三个核心能力：
class Base:
    # ① metadata = "注册中心"，记录了所有继承 Base 的模型信息
    metadata = MetaData()

    # ② 自动给子类加 __init__，让你能用 Book(title="三体", price=39.9) 创建实例
    #    （实际是 metaclass 在背后注入的，这里只是示意）

    # ③ 自动给子类加 __table__ 属性，指向数据库中的那张表
```

`Base` 本身几乎没有任何业务代码——它只是一个被 SQLAlchemy 改造过的空壳基类。真正的魔法在于**元类**（下文的 `DeclarativeMeta`），它在 `class Book(Base):` 被定义的瞬间，自动扫描 `Book` 类中的 `Column` 属性，把这些信息写入 `Base.metadata`。

换句话说：**`Base` 什么都不做，它只是"被继承"这个动作的触发器。** 你写 `class Book(Base)` 时，Python 解释器在执行这行代码的过程中，元类被唤醒，扫描你定义的列，登记到 `metadata`。这就是为什么你什么都不用调，SQLAlchemy 就知道你的表结构。

**"基类"是什么？**

所谓"基类"（父类），就是其他类继承的"模板类"。在 Python 里，`class Book(Base)` 表示 `Book` 继承自 `Base`——`Book` 会获得 `Base` 的所有方法和能力。

```python
# 普通 Python 类：只是一个自定义数据类型
class Book:                          # 不继承任何东西
    title = "三体"
# Book 就是一个普通类，和数据库没有任何关系

# 继承 Base 的类：变成一个"数据库表映射类"
class Book(Base):                    # 继承自 Base
    title = Column(String(100))
# Book 变成了一个 ORM 模型——SQLAlchemy 能识别它、操作它
```

**`declarative_base()` 做了什么？**

```python
from sqlalchemy.ext.declarative import declarative_base

Base = declarative_base()
```

这一行创建了一个**特殊的 Python 基类**。它被 SQLAlchemy 的"元类"（metaclass）改造过，带了自动收集 ORM 模型的能力。

**逐步理解——用代码模拟背后的原理**

```python
# === SQLAlchemy 内部简化逻辑（你不用写，理解即可） ===

class DeclarativeMeta(type):  # 元类：负责"创建类"的类
    def __new__(cls, name, bases, attrs):
        # 当任何 class XXX(Base): 被定义时，这个方法自动触发
        # name  = "Book"           ← 类名
        # bases = (Base,)          ← 父类
        # attrs = {                ← 类的所有属性
        #     "__tablename__": "books",
        #     "id": Column(Integer, ...),
        #     "title": Column(String(100), ...),
        # }
        
        # 扫描 attrs 中所有 Column 对象 → 知道这个表有哪些列
        # 把类名/表名/列信息存入 Base.metadata
        return super().__new__(cls, name, bases, attrs)

Base = declarative_base()  # 实际创建时指定了 DeclarativeMeta 作为元类
```

**你定义 `class Book(Base)` 时发生了什么？**

```
你写的代码                                  SQLAlchemy 自动做的事
─────────────────────────────────────────────────────────────────
class Book(Base):                          
    __tablename__ = "books"                ① 读取 __tablename__ → 表名叫 "books"
                                          ② 扫描所有 Column 属性：
    id = Column(Integer, ...)                发现列: id (Integer, 主键)
    title = Column(String(100), ...)         发现列: title (VARCHAR 100)
    price = Column(Float, ...)               发现列: price (FLOAT)
                                          ③ 把这些信息存入 Base.metadata
                                          ④ Book 类获得 .query() / .add() 等 ORM 能力
```

**`Base.metadata` 是什么？**

`Base.metadata` 是 SQLAlchemy 的"**注册中心**"，记录了所有 ORM 模型的表结构信息：

```python
from models import Book, User  # 只要 import 了，Base.metadata 就记录了它们

print(Base.metadata.tables)
# {
#     "books": Table("books", ...),     ← Book 模型自动注册到这里
#     "users": Table("users", ...),     ← User 模型自动注册到这里
# }

# 后面 create_all 就是遍历这个字典，为每个表生成 CREATE TABLE SQL
Base.metadata.create_all(bind=engine)
```

**一图总结 `Base` 的角色**

```
                          ┌────────────────────┐
                          │   declarative_base() │
                          │    创建基类           │
                          └──────────┬─────────┘
                                     │ 被继承
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
       class Book(Base)      class User(Base)      class Order(Base)
              │                      │                      │
              │ "我是 Book 类，       │ "我是 User 类，       │
              │  表名 = books，       │  表名 = users，       │
              │  列 = id/title/..."   │  列 = id/name/..."    │
              └──────────┬───────────┴──────────┬───────────┘
                         │                      │
                         ▼                      ▼
              ┌─────────────────────────────────────┐
              │         Base.metadata                │
              │  {                                   │
              │    "books":  <Table 对象>,            │
              │    "users":  <Table 对象>,            │
              │  }                                   │
              │  ↑ 自动收集所有 ORM 模型的表结构        │
              └─────────────────────────────────────┘
                         │
                         │  create_all(bind=engine) 遍历 metadata
                         ▼
              ┌─────────────────────────────────────┐
              │  CREATE TABLE IF NOT EXISTS books... │
              │  CREATE TABLE IF NOT EXISTS users... │
              └─────────────────────────────────────┘
```

**总结**：

| 概念 | 解释 | 类比 |
|------|------|------|
| `Base` | 所有 ORM 模型的公共父类 | 一个"登记表模板" |
| `class Book(Base)` | 继承 Base，成为 ORM 模型 | 在登记表上填了一行："Book → books 表，有 id/title 等列" |
| `Base.metadata` | 自动收集的"所有模型的登记信息" | 一张汇总表，记录了所有表和列的信息 |
| `create_all()` | 遍历 metadata，建表 | 用汇总表去"施工"——在数据库里建表 |

> **一句话**：`Base = declarative_base()` 创建了一个"带有自动登记能力"的父类。你写的每个 `class Xxx(Base)` 都会自动在 `Base.metadata` 里登记自己的表结构信息，最后 `create_all()` 拿着这些信息去数据库建表。

**④ `get_db()` — FastAPI 依赖注入用**

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()       # ① 创建一个新的数据库会话
    try:
        yield db              # ② 把会话传给路由函数使用（暂停在这里）
    finally:
        db.close()            # ③ 请求处理完后，无论成功/失败都会执行
```

这是搭配 FastAPI `Depends` 的标准写法。`yield` 之前是"准备资源"，`yield` 之后是"清理资源"。

```
请求进来
  ↓
db = SessionLocal()           ← 创建会话
  ↓
yield db                     ← 传给路由函数
  ↓
路由函数执行（add/query/commit...）
  ↓
db.close()                   ← 请求结束，关闭会话（finally 保证一定执行）
```

### 4.2 定义 ORM 模型（models.py）

#### 4.2.0 概念：Python 类 → 数据库表

在 SQLAlchemy 中，你定义一个 Python 类，它自动映射为一张数据库表：

```python
# 你写的 Python 代码                    # 对应数据库
class Book(Base):                      # CREATE TABLE books (
    __tablename__ = "books"           #
                                       #
    id = Column(Integer, primary_key)  #   id INTEGER PRIMARY KEY,
    title = Column(String(100))        #   title VARCHAR(100),
    price = Column(Float)              #   price FLOAT
                                       # );
```

> 核心规则：**一个类 = 一张表，一个属性 = 一个列**。

---

#### 4.2.1 完整模型定义

```python
# models.py - ORM 数据模型

from sqlalchemy import Column, Integer, String, Float, Boolean, DateTime, ForeignKey
from sqlalchemy.orm import relationship
from sqlalchemy.sql import func
from database import Base

class Book(Base):
    """图书 ORM 模型"""
    __tablename__ = "books"  # 数据库表名

    id = Column(Integer, primary_key=True, index=True, comment="图书 ID")
    title = Column(String(100), nullable=False, index=True, comment="书名")
    author = Column(String(50), nullable=False, comment="作者")
    price = Column(Float, nullable=False, comment="价格")
    description = Column(String(500), default="", comment="简介")
    is_published = Column(Boolean, default=True, comment="是否上架")
    created_at = Column(DateTime, server_default=func.now(), comment="创建时间")
    updated_at = Column(DateTime, server_default=func.now(), onupdate=func.now(), comment="更新时间")

    def __repr__(self):
        return f"<Book(id={self.id}, title='{self.title}')>"
```

> ### 🏗️ 项目实例：SyncHealth User ORM 模型（SQLAlchemy 2.0 风格）
>
> SyncHealth 使用 SQLAlchemy 2.0 的 `Mapped` + `mapped_column` 声明式语法，比传统 `Column()` 写法更类型安全：
>
> ```python
> # backend/app/models/user.py - SQLAlchemy 2.0 风格 ORM 模型
> from datetime import datetime, timezone
> from sqlalchemy import DateTime, Integer, String
> from sqlalchemy.orm import Mapped, mapped_column
> from app.database import Base
>
> class User(Base):
>     __tablename__ = "users"
>
>     id: Mapped[int] = mapped_column(Integer, primary_key=True, autoincrement=True)
>     email: Mapped[str] = mapped_column(String(255), unique=True, index=True, nullable=False)
>     hashed_password: Mapped[str] = mapped_column(String(255), nullable=False)
>     display_name: Mapped[str] = mapped_column(String(100), nullable=False)
>     created_at: Mapped[datetime] = mapped_column(DateTime, default=lambda: datetime.now(timezone.utc))
>     last_sync_at: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)
> ```
>
> `Mapped[int]` 让 IDE 知道 `user.id` 是 `int` 类型；`datetime | None` 语法比 `Optional[datetime]` 更简洁。

#### 4.2.2 Column 参数详解

每个 `Column()` 定义了一个数据库列，常用参数如下：

| 参数 | 含义 | 示例 | 等价 SQL |
|------|------|------|----------|
| `primary_key=True` | 主键 | `Column(Integer, primary_key=True)` | `PRIMARY KEY` |
| `nullable=False` | 不允许为空 | `Column(String, nullable=False)` | `NOT NULL` |
| `default=值` | Python 端默认值 | `Column(Boolean, default=True)` | 插入时 Python 侧设值 |
| `server_default=func` | 数据库端默认值 | `Column(DateTime, server_default=func.now())` | `DEFAULT NOW()` |
| `unique=True` | 唯一约束 | `Column(String, unique=True)` | `UNIQUE` |
| `index=True` | 创建索引 | `Column(Integer, index=True)` | `CREATE INDEX ...` |
| `onupdate=func` | 更新时自动设值 | `Column(DateTime, onupdate=func.now())` | `ON UPDATE NOW()` |
| `comment="说明"` | 列注释 | `Column(String, comment="书名")` | `COMMENT '书名'` |

**重点区分 `default` 和 `server_default`**

```python
# default → Python 层面给默认值，如果传了值就用你传的，没传就用默认值
is_active = Column(Boolean, default=True)

# server_default → 让数据库生成默认值（如时间戳）
# 这样即使你绕过 ORM 直接写 SQL，也会自动填充
created_at = Column(DateTime, server_default=func.now())
```

#### 4.2.3 常用 Column 类型对照

| Python 类型 | SQLAlchemy 类型 | SQLite | MySQL | PostgreSQL |
|-------------|-----------------|--------|-------|------------|
| `int` | `Integer` | INTEGER | INT | INTEGER |
| `str` | `String(n)` | TEXT | VARCHAR(n) | VARCHAR(n) |
| `str`（大量文本） | `Text` | TEXT | TEXT | TEXT |
| `float` | `Float` | REAL | FLOAT | FLOAT |
| `bool` | `Boolean` | INTEGER(0/1) | TINYINT | BOOLEAN |
| `datetime` | `DateTime` | TEXT(ISO格式) | DATETIME | TIMESTAMP |
| `bytes` | `LargeBinary` | BLOB | BLOB | BYTEA |
| 枚举 | `Enum` | TEXT | ENUM | ENUM |

#### 4.2.4 `__repr__` 方法的作用

```python
def __repr__(self):
    return f"<Book(id={self.id}, title='{self.title}')>"
```

定义了对象在 `print()` 或调试时的显示格式：

```python
book = Book(id=1, title="三体")

# 有 __repr__：

```

### 4.3 创建表（main.py 启动时）

```python
# main.py - 应用启动时创建表
from database import engine, Base
from models import Book, User  # 必须导入模型，否则 Base 不知道有哪些表

# 创建所有表（如果不存在）
# ⚠️ 生产环境请使用 Alembic 迁移工具
Base.metadata.create_all(bind=engine)

app = FastAPI()
```

**`create_all` 做了什么？**

1. `Base.metadata` 记录了所有继承自 `Base` 的模型
2. `create_all(bind=engine)` 遍历所有模型，对每个模型生成 `CREATE TABLE IF NOT EXISTS ...` SQL
3. 表已存在则跳过，不存在则创建

```
你定义了 → class Book(Base):    __tablename__ = "books"
                          ↓
          Base.metadata 自动收集
                          ↓
          create_all() 生成 SQL：
          CREATE TABLE IF NOT EXISTS books (
              id INTEGER PRIMARY KEY,
              title VARCHAR(100) NOT NULL,
              ...
          )
```

> **⚠️ 警告**：`create_all` 只创建不存在的表，**不会修改已有表的结构**。比如你新增了一个列，`create_all` 不会自动加。生产环境请使用 **Alembic** 进行数据库迁移。

### 4.4 CRUD 操作完整示例

#### 4.4.0 前置概念：Pydantic Schema vs ORM Model

在动手写 CRUD 之前，先理解两种"模型"的区别：

```
┌─────────────────────────┐    ┌─────────────────────────┐
│    Pydantic Schema       │    │    SQLAlchemy Model      │
│    (schemas.py)          │    │    (models.py)           │
├─────────────────────────┤    ├─────────────────────────┤
│ 作用：校验 HTTP 请求/响应  │    │ 作用：映射数据库表        │
│ 继承自：BaseModel         │    │ 继承自：Base             │
│ 数据来源：客户端 JSON      │    │ 数据来源：数据库行         │
│ 生命周期：一次请求         │    │ 生命周期：数据库持久化     │
│                          │    │                          │
│ class BookCreate:        │    │ class Book:              │
│     title: str           │    │     __tablename__="books"│
│     price: float         │    │     title = Column(...)  │
│                          │    │     price = Column(...)  │
└─────────────────────────┘    └─────────────────────────┘

数据流向：
请求 JSON → BookCreate（校验）→ Book（ORM）→ 数据库
数据库 → Book（ORM）→ BookResponse（过滤）→ JSON 响应
```

> **为什么要分开？** 创建时可能有 `password` 字段，但返回时绝不能有。请求校验和响应过滤关注点不同，用不同的模型就能让代码更安全、更清晰。

---

#### 4.4.1 Pydantic Schema 定义

```python
from pydantic import BaseModel, Field
from typing import Optional

class BookCreate(BaseModel):
    """创建图书时接收的字段"""
    title: str = Field(min_length=1, max_length=100)
    author: str = Field(min_length=1, max_length=50)
    price: float = Field(gt=0)
    description: Optional[str] = Field(None, max_length=500)

class BookResponse(BaseModel):
    """返回给客户端的字段（多了一个 id，且不暴露内部字段）"""
    id: int
    title: str
    author: str
    price: float
    description: str
    is_published: bool

    class Config:
        from_attributes = True  # 🔑 关键配置：允许从 ORM 对象直接创建

class BookUpdate(BaseModel):
    """更新图书——所有字段都是可选的（传哪个改哪个）"""
    title: Optional[str] = Field(None, min_length=1, max_length=100)
    author: Optional[str] = Field(None, min_length=1, max_length=50)
    price: Optional[float] = Field(None, gt=0)
    description: Optional[str] = Field(None, max_length=500)
```

#### 4.4.2 `from_attributes = True` 是什么？

```python
class BookResponse(BaseModel):
    class Config:
        from_attributes = True  # Pydantic V1 叫 orm_mode = True
```

这行配置告诉 Pydantic："你可以从 SQLAlchemy ORM 对象读取属性来构建模型"。

```python
# 有了 from_attributes = True
orm_book = db.query(Book).first()       # SQLAlchemy 对象
response = BookResponse.from_orm(orm_book)  # ✅ 自动提取 id/title/author...
return response

# 实际上你不需要手动调 .from_orm()，FastAPI 在 response_model 中自动处理
@app.get("/books/{id}", response_model=BookResponse)
def get_book(id: int, db = Depends(get_db)):
    return db.query(Book).filter(Book.id == id).first()
    # ↑ 直接返回 ORM 对象，FastAPI 自动用 BookResponse 过滤字段
```
response_model是固定关键字，不能改名，response_model 叫响应模型，用来约束后端返回给前端的数据格式

#### 4.4.3 创建 CREATE — `db.add()` + `db.commit()` + `db.refresh()`

```python
@app.post("/books/", response_model=BookResponse, status_code=201)
def create_book(book: BookCreate, db: Session = Depends(get_db)):
    """
    创建图书 → 实际 SQL: INSERT INTO books (...) VALUES (...)
    """
    # ① 把 Pydantic 数据转成 ORM 模型对象
    db_book = Book(**book.model_dump())
    # book.model_dump() → {"title":"三体","author":"刘慈欣","price":39.9}
    # Book(**dict)      → Book(title="三体", author="刘慈欣", price=39.9)

    # ② 添加到会话（暂存，还没写入数据库）
    db.add(db_book)          # 等价于：记录下"待插入一条数据"

    # ③ 提交事务（真正写入数据库）
    db.commit()              # 等价于：执行 INSERT，数据写入磁盘

    # ④ 刷新对象（重新从数据库读取，获取自动生成的值）
    db.refresh(db_book)      # 此时 db_book.id 才有值（数据库自增生成的）

    return db_book           # FastAPI 用 BookResponse 过滤后返回
```

**三步执行流程详解**：

```
db.add(book)     →  把 book 对象放入 Session 的"待办列表"
                    此时还没有执行 SQL，只是"标记了这个操作"
                    book.id 此时为 None（还没插入数据库）

db.commit()      →  把 Session 中所有"待办"操作打包成一个事务执行
                    实际执行: INSERT INTO books (title, author, price) VALUES (?, ?, ?)
                    数据写入磁盘，book.id 在数据库中生成（但由于没 refresh，Python 对象还不知道）

db.refresh(book) →  重新从数据库读取这条记录
                    实际执行: SELECT * FROM books WHERE id = ?
                    book.id 现在有值了（如 1），created_at 也有了
```

> **类比**：`add` = 点了外卖，`commit` = 商家接单开始做，`refresh` = 拿到外卖确认里面的东西都对。

#### 4.4.4 查询 READ — 链式调用
只要是函数参数，不属于路径占位符 {xxx}，默认全部归类为URL 查询参数。那为什么search、skip、limit 绝对不适合做成路径参数呢？
答：原因 1：搜索、分页是可选附加条件，不是资源唯一标识 原因 2：筛选条件可以随意增减，查询参数扩展性更强。
eg：
/books?search=三体&min_price=20&sort=price



```python
@app.get("/books/", response_model=list[BookResponse])
def list_books(
    skip: int = 0,              # 跳过前 N 条 = 翻页
    limit: int = 20,            # 最多返回 N 条 = 每页大小
    search: Optional[str] = None,
    db: Session = Depends(get_db)
):
    """获取图书列表（支持搜索和分页）"""
    query = db.query(Book)                       # ① 创建查询对象

    if search:                                    # ② 动态追加条件
        query = query.filter(
            Book.title.contains(search) |         # 书名包含关键字
            Book.author.contains(search)          # 或作者包含关键字
        )

    total = query.count()                         # ③ 符合条件的总数
    books = query.offset(skip).limit(limit).all() # ④ 分页 + 执行查询

    return books
```

**链式调用的本质**：

```python
# 每条 .filter() .offset() .limit() 都返回一个新的查询对象
# 相当于一直在给一个 SQL 语句追加子句

db.query(Book)                                    # SELECT * FROM books
    .filter(Book.is_published == True)            # WHERE is_published = true
    .filter(Book.price > 10)                      # AND price > 10
    .order_by(Book.price.desc())                  # ORDER BY price DESC
    .offset(0).limit(10)                          # LIMIT 10 OFFSET 0
    .all()                                        # 执行查询，返回列表
```

**终结方法：`.first()` `.all()` `.one()` `.scalar()`**

链式调用到最后必须用一个**终结方法**来真正执行 SQL。下面的四个方法是查询时最常用的：

---

**① `.all()` — 获取全部结果**

```python
books = db.query(Book).filter(Book.price > 20).all()
# → [<Book id=1>, <Book id=3>, <Book id=5>]  返回列表，空列表表示没有匹配
```

- **含义**：执行查询，返回**所有**匹配的记录，放到一个 Python 列表中
- **对应 SQL**：就是正常的 `SELECT * FROM books WHERE price > 20`
- **什么时候用**：查列表（列表页、搜索结果、导出全部数据等）
- **结果为空**：返回空列表 `[]`，不会报错

---

**② `.first()` — 只取第一条**

```python
book = db.query(Book).filter(Book.id == 1).first()
# → <Book id=1> 或 None
```

- **含义**：执行查询并只返回**第一条**记录，自动加 `LIMIT 1`
- **对应 SQL**：`SELECT * FROM books WHERE id = 1 LIMIT 1`
- **什么时候用**：根据唯一条件查单条（如 `id`、`username`），不需要全部结果
- **结果为空**：返回 `None`，**不会报错** → 所以查完要手动判空：`if not book: raise 404`

---

**③ `.one()` — 严格要求恰好一条**

```python
book = db.query(Book).filter(Book.id == 1).one()
# → <Book id=1>  ← 恰好一条，正常返回

# 如果查不到：
db.query(Book).filter(Book.id == 9999).one()
# → 抛出 NoResultFound 异常 💥

# 如果查出多条：
db.query(Book).filter(Book.price > 10).one()
# → 抛出 MultipleResultsFound 异常 💥
```

- **含义**：要求结果**必须有且只有一条**，否则直接抛异常
- **对应 SQL**：和 `.first()` 一样执行查询，但会额外检查结果数量
- **什么时候用**：你的业务逻辑**严格依赖恰好一条数据**的场景（如转账操作中的账户记录），用 `.one()` 能提前暴露数据异常
- **与 `.first()` 的区别**：`.first()` 温柔，查不到返回 `None`；`.one()` 严格，不满足预期就直接炸

---

**④ `.scalar()` — 只取第一行的第一个字段值**

```python
# 查询图书总数
total = db.query(func.count(Book.id)).scalar()
# → 15  ← 返回纯数字，不是对象

# 查询某个作者的名称
name = db.query(Book.author).filter(Book.id == 1).scalar()
# → "刘慈欣"  ← 返回纯字符串
```

- **含义**：返回查询结果的**第一行、第一个字段的原始值**（不是 ORM 对象）
- **什么时候用**：聚合查询（`COUNT`、`SUM`、`MAX`）或只需要一个值的场景
- **结果为空**：返回 `None`

---

**📊 汇总对比**

| 方法 | 返回类型 | 查不到时 | 查到多条时 | 典型场景 |
|------|----------|----------|------------|----------|
| `.all()` | `list[对象]` | 返回 `[]` | 全部返回 | 列表页 / 搜索 |
| `.first()` | 对象 或 `None` | 返回 `None` | 返回第一条 | 按 ID 查单条 |
| `.one()` | 对象 | 抛异常 | 抛异常 | 必须恰好一条 |
| `.scalar()` | 单个值 或 `None` | 返回 `None` | 返回第一条的首字段值 | COUNT / 聚合 |

#### 4.4.5 更新 UPDATE — `setattr` + `exclude_unset`

```python
@app.put("/books/{book_id}", response_model=BookResponse)
def update_book(book_id: int, book_update: BookUpdate, db: Session = Depends(get_db)):
    # ① 先查出来
    db_book = db.query(Book).filter(Book.id == book_id).first()
    if not db_book:
        raise HTTPException(status_code=404, detail="图书不存在")

    # ② 只更新实际传了的字段（exclude_unset=True 是关键）
    update_data = book_update.model_dump(exclude_unset=True)
    # exclude_unset=True → 只包含用户实际传了的字段
    # 例如用户只传了 {"price": 29.9}，则 update_data = {"price": 29.9}
    # title/author 不在 update_data 中，不会被覆盖

    for field, value in update_data.items():
        setattr(db_book, field, value)   # 等价于: db_book.price = 29.9

    # ③ 提交
    db.commit()
    db.refresh(db_book)
    return db_book
```

**`exclude_unset=True` 为什么重要？**

```python
# 场景：BookUpdate 有 title/author/price 三个可选字段
# 用户只想改价格，发来：{"price": 29.9}

# ❌ 不用 exclude_unset
update_data = book_update.model_dump()
# → {"title": None, "author": None, "price": 29.9}
# title 和 author 会被错误地设为 None！

# ✅ 使用 exclude_unset
update_data = book_update.model_dump(exclude_unset=True)
# → {"price": 29.9}
# 只有用户明确传了的字段才更新
```

#### 4.4.6 删除 DELETE — `db.delete()`

```python
@app.delete("/books/{book_id}", status_code=status.HTTP_204_NO_CONTENT)
def delete_book(book_id: int, db: Session = Depends(get_db)):
    db_book = db.query(Book).filter(Book.id == book_id).first()
    if not db_book:
        raise HTTPException(status_code=404, detail="图书不存在")

    db.delete(db_book)   # ① 标记为删除
    db.commit()          # ② 执行 DELETE FROM books WHERE id = ?
    # ③ 返回 204 No Content——删除成功，无需返回内容
```

**删除操作的特点**：
- `db.commit()` 后数据就没了，不可恢复
- 204 状态码 = "请求成功，但没有响应体"
- 如果删除后调用 `db.refresh()` 会报错（因为记录已被删除）

### 4.6 SQLAlchemy 常见的坑与最佳实践

#### ⚠️ 坑 1：在 `commit()` 之前读取自增 ID

```python
# ❌ 错误：id 还没生成
book = Book(title="三体")
db.add(book)
print(book.id)  # None——还没 commit，数据库还没生成 id

# ✅ 正确
db.add(book)
db.commit()
db.refresh(book)
print(book.id)  # 42——刷新后拿到了数据库生成的值
```

#### ⚠️ 坑 2：忘记 `commit()` 导致数据丢失

```python
# ❌ 错误：数据没写入数据库
book = Book(title="三体")
db.add(book)
# 函数结束 → get_db 的 finally 执行 db.close()
# 数据丢了！

# ✅ 正确：add 之后必须 commit
db.add(book)
db.commit()
```

#### ⚠️ 坑 3：在循环中逐条 `add` + `commit`

```python
# ❌ 慢：每条数据一次 commit
for title in titles:
    db.add(Book(title=title))
    db.commit()  # 每次都开事务，非常慢

# ✅ 快：批量 add，一次 commit
for title in titles:
    db.add(Book(title=title))
db.commit()  # 一次性提交所有
```

#### ⚠️ 坑 4：`model_dump()` vs `dict()`

```python
# Pydantic V2 正确用法
book = BookCreate(title="三体", author="刘慈欣", price=39.9)
book.model_dump()           # ✅ V2 推荐
# → {"title": "三体", "author": "刘慈欣", "price": 39.9}

# Pydantic V1 旧写法（V2 仍兼容但不推荐）
book.dict()                  # ⚠️ V1 写法
```

#### ✅ 最佳实践总结

1. **Schema 和 Model 分离** — `BookCreate` 校验请求，`BookResponse` 过滤响应，`Book` ORM 模型操作数据库
2. **先查再改** — 更新/删除前必须先 `filter().first()` 判断是否存在
3. **`from_attributes = True`** — 响应模型必须配这个，否则从 ORM 对象构建会报错
4. **`exclude_unset=True`** — 更新接口必须用，防止把没传的字段设成 None
5. **开发时 `echo=True`** — 看到实际执行的 SQL 才能判断是否有 N+1 问题
6. **生产环境用 Alembic** — 别用 `create_all` 做表变更

## 5. JWT OAuth2 认证授权

### 5.0 什么是 JWT？

JWT（JSON Web Token）是一种无状态的认证方式：

```
JWT 结构（三个部分，用 . 分隔）：
eyJhbG...    .    eyJzdW...    .    SflKxw...
   ↑              ↑                ↑
 Header        Payload         Signature
（算法类型）    （用户数据）      （签名防篡改）

工作流程：
1. 用户登录 → 服务器验证用户名密码 → 生成 JWT → 返回给客户端
2. 客户端存储 JWT（通常存在 localStorage）
3. 后续请求携带 JWT：Authorization: Bearer <token>
4. 服务器验证 JWT 签名 → 提取用户信息 → 处理请求
```

### 5.1 安装依赖

```powershell
pip install python-jose[cryptography] passlib[bcrypt] python-multipart
```

### 5.2 JWT 工具函数

在开始编写认证端点之前，需要先封装 JWT 的底层操作。这一节定义四个核心工具函数，它们构成了认证系统的基础：

- **`verify_password` / `get_password_hash`**：使用 `passlib` 库对密码进行哈希和验证。注意：密码永远不能以明文存储到数据库，`bcrypt` 算法会自动加入随机盐，即使两个用户的密码相同，哈希值也不同，无法逆推出原文。
- **`create_access_token`**：将用户数据（放入 `sub` 字段，JWT 规范中的"主体"字段）和过期时间（`exp` 字段）编码为 JWT 字符串。过期时间通常设 15-30 分钟，过短影响体验、过长有安全风险。
- **`verify_token`**：解码并验证 JWT，检查签名是否被篡改、是否过期。验证通过返回 payload 中的数据，失败返回 `None`。

生产环境务必注意：`SECRET_KEY` 必须从环境变量读取，不要硬编码在代码中，以免泄露后所有 token 可被伪造。

```python
# auth_utils.py - JWT 认证工具

from datetime import datetime, timedelta
from typing import Optional
from jose import JWTError, jwt
from passlib.context import CryptContext

# 配置（生产环境从环境变量读取！）
SECRET_KEY = "your-secret-key-change-in-production-必须修改"
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 30

# 密码哈希上下文
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """验证密码"""
    return pwd_context.verify(plain_password, hashed_password)

def get_password_hash(password: str) -> str:
    """生成密码哈希"""
    return pwd_context.hash(password)

def create_access_token(data: dict, expires_delta: Optional[timedelta] = None) -> str:
    """
    创建 JWT token
    data = {"sub": "username"}  # sub 是 JWT 标准字段，表示主体
    """
    to_encode = data.copy()
    expire = datetime.utcnow() + (expires_delta or timedelta(minutes=15))
    to_encode.update({"exp": expire})
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

def verify_token(token: str) -> Optional[dict]:
    """验证 JWT token，返回 payload 或 None"""
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username: str = payload.get("sub")
        if username is None:
            return None
        return {"username": username}
    except JWTError:
        return None
```

> ### 🏗️ 项目实例：SyncHealth JWT + bcrypt 安全模块
>
> SyncHealth 采用 **JWT 双令牌**（access + refresh）方案。`create_access_token` 生成短时效的 access token（60分钟），`create_refresh_token` 生成长时效的 refresh token（30天）。`decode_token` 设置 `verify_sub=False` 允许 `sub` 字段为非字符串：
>
> ```python
> # backend/app/core/security.py - JWT + bcrypt 完整实现
> import bcrypt, jwt
> from datetime import datetime, timedelta, timezone
> from app.config import settings
>
> def hash_password(password: str) -> str:
>     pwd_bytes = password.encode("utf-8")[:72]  # bcrypt 限制 72 字节
>     salt = bcrypt.gensalt()
>     return bcrypt.hashpw(pwd_bytes, salt).decode("utf-8")
>
> def verify_password(plain_password: str, hashed_password: str) -> bool:
>     return bcrypt.checkpw(plain_password.encode("utf-8")[:72], hashed_password.encode("utf-8"))
>
> def create_access_token(data: dict) -> str:
>     to_encode = data.copy()
>     expire = datetime.now(timezone.utc) + timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES)
>     to_encode.update({"exp": expire, "type": "access"})
>     return jwt.encode(to_encode, settings.SECRET_KEY, algorithm=settings.JWT_ALGORITHM)
>
> def create_refresh_token(data: dict) -> str:
>     to_encode = data.copy()
>     expire = datetime.now(timezone.utc) + timedelta(days=settings.REFRESH_TOKEN_EXPIRE_DAYS)
>     to_encode.update({"exp": expire, "type": "refresh"})
>     return jwt.encode(to_encode, settings.SECRET_KEY, algorithm=settings.JWT_ALGORITHM)
>
> def decode_token(token: str) -> dict:
>     return jwt.decode(token, settings.SECRET_KEY, algorithms=[settings.JWT_ALGORITHM],
>                       options={"verify_sub": False})
> ```
>
> 配置由 `pydantic-settings` 管理，支持从 `.env` 文件读取 `SECRET_KEY`：
>
> ```python
> # backend/app/config.py - Settings
> class Settings(BaseSettings):
>     JWT_ALGORITHM: str = "HS256"
>     ACCESS_TOKEN_EXPIRE_MINUTES: int = 60
>     REFRESH_TOKEN_EXPIRE_DAYS: int = 30
>     model_config = {"env_file": ".env"}
> ```

### 5.3 OAuth2 认证端点

这一节将 5.2 的工具函数组装成实际的登录和注册接口。涉及几个关键组件：

- **`OAuth2PasswordBearer`**：定义 token 的提取方式。它会从请求头 `Authorization: Bearer <token>` 中自动解析出 token 字符串。`tokenUrl` 参数指向登录接口路径，用于 Swagger UI 的 "Authorize" 按钮——点击后会自动弹窗让你输入用户名密码。
- **`OAuth2PasswordRequestForm`**：标准 OAuth2 登录表单。它接收 `application/x-www-form-urlencoded` 格式的 `username` 和 `password` 字段（不是 JSON 格式），这是 OAuth2 规范的固定格式。在 Swagger UI 中直接可用。
- **`get_current_user` 依赖**：混合使用 `Depends(oauth2_scheme)` 提取 token 和 `Depends(get_db)` 获取数据库会话——依赖注入的灵活组合。它验证 token → 解析用户名 → 查数据库 → 返回用户对象，后续所有需要登录的接口只需声明 `Depends(get_current_user)` 即可。

下面实现完整的登录（返回 JWT token）、注册（创建用户）、以及认证依赖函数：

```python
# auth.py - 认证路由

from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm
from sqlalchemy.orm import Session
from database import get_db
from models import User
from auth_utils import (
    verify_password, get_password_hash,
    create_access_token, verify_token,
    ACCESS_TOKEN_EXPIRE_MINUTES
)

router = APIRouter(prefix="/auth", tags=["认证"])

# OAuth2 方案：从请求头提取 token
# tokenUrl = 登录接口路径（用于 Swagger 文档的 Authorize 按钮）
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")

# === 依赖：获取当前用户 ===
def get_current_user(
    token: str = Depends(oauth2_scheme),
    db: Session = Depends(get_db)
):
    """
    从请求头 Authorization: Bearer <token> 中提取并验证 token
    返回当前登录用户
    """
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="无法验证凭据",
        headers={"WWW-Authenticate": "Bearer"},
    )

    payload = verify_token(token)
    if payload is None:
        raise credentials_exception

    username = payload.get("username")
    user = db.query(User).filter(User.username == username).first()
    if user is None:
        raise credentials_exception

    return user

# === 登录接口 ===
@router.post("/login")
def login(
    form_data: OAuth2PasswordRequestForm = Depends(),
    db: Session = Depends(get_db)
):
    """
    用户登录 → 返回 access_token
    
    OAuth2PasswordRequestForm 自动解析表单字段：
    - username
    - password
    - grant_type（可选）
    - scope（可选）
    """
    # 查找用户
    user = db.query(User).filter(
        User.username == form_data.username
    ).first()

    # 验证用户和密码
    if not user or not verify_password(form_data.password, user.hashed_password):
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="用户名或密码错误",
            headers={"WWW-Authenticate": "Bearer"},
        )

    # 生成 token
    access_token = create_access_token(
        data={"sub": user.username},
        expires_delta=timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    )

    return {
        "access_token": access_token,
        "token_type": "bearer",
        "username": user.username
    }

# === 注册接口 ===
@router.post("/register", status_code=status.HTTP_201_CREATED)
def register(
    username: str,
    email: str,
    password: str,
    db: Session = Depends(get_db)
):
    """用户注册"""
    # 检查用户名是否已存在
    if db.query(User).filter(User.username == username).first():
        raise HTTPException(status_code=400, detail="用户名已存在")

    # 检查邮箱是否已存在
    if db.query(User).filter(User.email == email).first():
        raise HTTPException(status_code=400, detail="邮箱已被注册")

    # 创建用户
    user = User(
        username=username,
        email=email,
        hashed_password=get_password_hash(password)
    )
    db.add(user)
    db.commit()
    db.refresh(user)

    return {"message": "注册成功", "username": username}
```

### 5.4 使用认证保护接口

有了 `get_current_user` 依赖后，保护接口变得极其简单——只需在路由函数参数中声明 `current_user = Depends(get_current_user)`。如果请求没有携带有效的 token，`get_current_user` 会自动抛出 401 错误，路由函数根本不会执行。

这种模式的优势在于：
- **零入侵**：路由函数只需要声明需要当前用户，不关心 token 怎么提取、怎么验证——这些都由依赖链处理。
- **统一保护**：所有需要登录的接口共用同一个 `get_current_user` 依赖，认证逻辑只写一次。
- **灵活组合**：可以同时注入多个依赖，如 `current_user`（认证）+ `db`（数据库会话）组合使用。

> ### 🏗️ 项目实例：SyncHealth Service 层 CRUD + 路由层认证组合
>
> SyncHealth 采用 **Service 层 + Router 层** 分离架构：Service 层处理业务逻辑（数据库操作 + 异常抛出），Router 层处理 HTTP 细节（路由注册 + 依赖注入）：
>
> ```python
> # backend/app/services/auth_service.py - Service 层：纯业务逻辑
> from app.core.exceptions import ConflictException, UnauthorizedException
>
> async def register_user(db, email, password, display_name):
>     result = await db.execute(select(User).where(User.email == email))
>     if result.scalar_one_or_none():
>         raise ConflictException("Email already registered")  # 自动 → 409
>
>     user = User(email=email, hashed_password=hash_password(password), display_name=display_name)
>     db.add(user)
>     await db.flush()  # 获取 user.id（不 commit，外层统一管理事务）
>
>     access_token = create_access_token({"sub": user.id, "email": user.email})
>     refresh_token = create_refresh_token({"sub": user.id, "email": user.email})
>     return user, access_token, refresh_token
>
>
> # backend/app/api/auth.py - Router 层：HTTP 映射
> from app.services.auth_service import register_user, login_user
>
> @router.post("/register", response_model=TokenResponse)
> async def register(data: UserRegister, db: AsyncSession = Depends(get_db)):
>     user, access_token, refresh_token = await register_user(db, data.email, data.password, data.display_name)
>     return TokenResponse(access_token=access_token, refresh_token=refresh_token)
>
> @router.post("/login", response_model=TokenResponse)
> async def login(data: UserLogin, db: AsyncSession = Depends(get_db)):
>     user, access_token, refresh_token = await login_user(db, data.email, data.password)
>     return TokenResponse(access_token=access_token, refresh_token=refresh_token)
> ```
>
> `db.flush()`（而非 `db.commit()`）在 Service 层生成 `user.id` 但不提交事务，外层 `get_db` 的 `yield` 统一 commit/rollback。这保证了整个请求的事务性。

下面演示获取用户资料（需要登录）和创建图书（需要登录 + 数据库）两个典型场景：

```python
# main.py - 在路由中使用认证依赖

from auth import router as auth_router, get_current_user
from models import User

app.include_router(auth_router)

@app.get("/profile")
def read_profile(current_user: User = Depends(get_current_user)):
    """获取当前用户信息（需要登录）"""
    return {
        "id": current_user.id,
        "username": current_user.username,
        "email": current_user.email
    }

@app.post("/books/")
def create_book(
    book: BookCreate,
    current_user: User = Depends(get_current_user),
    db: Session = Depends(get_db)

    """创建图书（需要登录）"""
    # current_user 包含当前登录用户的信息
    db_book = Book(**book.model_dump())
    db.add(db_book)
    db.commit()
    db.refresh(db_book)
    return db_book
```

## 📝 第3阶段总结

### 核心知识点速查

| 概念 | 用途 | 关键代码 |
|------|------|----------|
| `Depends()` | 依赖注入 | `db: Session = Depends(get_db)` |
| 函数依赖 | 可复用逻辑 | `def common_params(): ...` |
| 类依赖 | 有状态的依赖 | `class Pagination: ...` |
| yield 依赖 | 资源清理 | `yield db` → `finally: db.close()` |
| 中间件 | 请求拦截 | `@app.middleware("http")` |
| CORS | 跨域配置 | `CORSMiddleware` |
| `BackgroundTasks` | 异步任务 | `background_tasks.add_task(...)` |
| SQLAlchemy | ORM 数据库 | `Session.query().filter()` |
| JWT | 无状态认证 | `jwt.encode() / jwt.decode()` |

### 最佳实践

1. **依赖要小而专注** - 每个依赖只做一件事
2. **安全相关用依赖注入** - 避免在每个接口中重复认证代码
3. **中间件不要做重逻辑** - 只做横切关注点（日志、计时、CORS）
4. **密码必须哈希** - 永远不要存储明文密码
5. **JWT token 设过期时间** - 不要太长（15-30 分钟）
6. **SECRET_KEY 从环境变量读取** - 不要硬编码在代码中
